## Summary

P03 adds kernel-owned `cordis.run_events` and `cordis.run_waits` side tables plus two SQL verbs: claim-fenced `cordis.await_event(...)` and unfenced `cordis.emit_event(...)` for UI/callback emitters. Waiting acquires locks in the global order **event key → jobs row → wait row**, appends `run/await` while the claim is still live, registers one active wait per run, then changes the existing `cordis.jobs` row to `WAITING` and clears its lease in the same transaction. Emission serializes on the same event-key row, records one canonical `event/emit` in `cordis.agent_steps`, applies a payload-NULL first-write-wins fence, appends one kernel `run/wake` per matching waiter, returns all such jobs to `PENDING`, and removes their active wait registrations atomically. Events persist and fan out; emit-before-wait is resolved immediately by appending a `run/await`/`run/wake` pair without yielding the caller’s claim. The event table caches payload only as the first-write fence; the canonical payload remains the log row identified by the event’s source pointer. This is a targeted numbered-SQL addition, not a queue, log, claim, apply-tool, or plugin-catalog refactor.

P03 is complete when the automated tests prove:

1. wait registration, `run/await`, `WAITING`, and claim release commit or roll back together;
2. an emitted event wakes every matching waiter exactly once;
3. emit-before-wait resolves without changing the caller from `RUNNING`;
4. duplicate emit preserves the first payload and adds no duplicate wake;
5. duplicate wait cannot retarget one scheduler row or duplicate its log history;
6. a `WAITING` row is untouched by stale-lease reap and remains unclaimable;
7. wait and emit races have no deadlock and no missed wake;
8. the full product still contains one jobs queue and one direct log insert implementation.

### F protocol order: semantic contract, not ABI

`docs/analysis/2026-08-23-f-yield-loop-protocol-sketch.md` §7 defines the semantic order.

Wait:

1. authorize event await — deferred to P07/P08;
2. check whether the event is already committed;
3. append `run/await`;
4. persist wait registration in the same transaction;
5. set jobs to `WAITING`;
6. clear claim ownership and commit.

Emit:

1. authorize event emission — deferred to P07/P08;
2. establish first-write-wins on the exact event key;
3. append canonical `event/emit`;
4. for each matched waiter, append kernel `run/wake`;
5. change its jobs row from `WAITING` to `PENDING` with `available_at = now()`.

The emitter invokes `emit_event`; it does not append `run/wake` itself. The kernel function owns wake production.

F §10 declares these states illegal:

- an active wait exists but the claim remains live;
- a claim is cleared but the wait is not durable;
- emit and a future timeout both wake the same wait.

P03 enforces the first two. P04 must use P03’s lock order and status/await-ID fences to enforce the third when timeout resolution is added.

F §11 keeps scheduler state on jobs:

```text
PENDING --claim--> RUNNING
RUNNING --await--> WAITING
WAITING --emit--> PENDING
```

The optional `wake_event_scope` and `wake_event_name` columns in the older F object sketch are superseded by D3 B and must not be added to `cordis.jobs`.

### What P01 already shipped

`sql/0001_p01_claim.sql` supplies the scheduler invariants P03 composes with:

- `cordis.jobs.run_id` is unique, including terminal rows.
- Status already permits `WAITING` and `SLEEPING`.
- `jobs_claim_fields_check` requires all claim fields exactly when status is `RUNNING`; a `WAITING` row must have all claim fields null.
- `claim_job` selects only due `PENDING` rows.
- `release_stale` only reaps expired `RUNNING` rows.
- `yield_claim`, `complete_claim`, `fail_claim`, and `renew_claim` all fence on a live `RUNNING` claim token.
- `jobs_ready_idx` indexes only `PENDING`.
- `renew_claim` is an absolute lease reset.
- P02 claim-aware append/checkpoint uses `GREATEST` to avoid shortening a longer lease.

P03 will use the P02-style `GREATEST` rule for the short pre-await lease extension. This extension prevents the claim from expiring between the ownership check and the log append. A suspended wait clears the lease later in the same transaction; an immediate resolution retains the non-shortened lease.

P01 does not append terminal or claim-timeout log rows. P03 must not infer historical completion from jobs status or attempt to repair that pre-existing P01/P02 integration gap.

### What P02 already shipped

`sql/0002_p02_log.sql` provides:

- the append-only `cordis.agent_steps` history;
- event kinds `run/await`, `run/wake`, and `event/emit`;
- `cordis.emit_step`, the sole direct insert implementation;
- `cordis.emit_step_claimed`, which only works while jobs remains live `RUNNING`;
- `cordis.run_state`, currently returning `final`, `error`, or `in-progress`;
- nullable `step_name` for P03 event kinds.

P03 must call `emit_step` after it has itself locked and fenced the jobs row. It must not call `emit_step_claimed` after changing the job to `WAITING`, and it must never insert into `agent_steps` directly.

The wait ordering is therefore:

```text
event-key lock
→ live jobs-row lock and lease extension
→ emit_step(run/await)
→ insert run_waits
→ jobs RUNNING → WAITING and clear claim fields
```

The immediate-resolve ordering is:

```text
event-key lock
→ live jobs-row lock and lease extension
→ emit_step(run/await)
→ emit_step(run/wake)
→ leave jobs RUNNING
```

### Current control flow

Before P03, P01/P02 can produce a `run/await` log row manually, but no product function connects it to scheduler state. `WAITING` is accepted by the jobs constraint but has no transition verb. `event/emit` and `run/wake` are accepted log kinds but have no first-write fence or wake implementation.

After P03, the normal flow is:

```text
worker already owns RUNNING claim
  → cordis.await_event(...)
      → event sentinel/key lock
      → live jobs-row lock
      → run/await append
      → active wait insert
      → jobs WAITING + claim fields cleared
  → commit

UI/callback
  → cordis.emit_event(...)
      → same event-key lock
      → event/emit append + event fence
      → for every matched wait:
           jobs lock
           wait-row lock
           run/wake append
           jobs PENDING
           delete active wait
  → commit

worker
  → cordis.claim_job(...)
  → fold sees run/await + run/wake
```

Emit-before-wait uses the same event key but takes the other branch:

```text
UI/callback emits event first
  → canonical event/emit committed

worker later calls await_event
  → event is already emitted
  → append run/await
  → append run/wake with source pointer
  → do not insert run_waits
  → do not clear claim
  → return canonical payload immediately
```

### Mutation points

P03 adds exactly these mutation paths:

1. `await_event`
   - may create a non-emitted event sentinel;
   - extends a live claim without shortening it;
   - appends `run/await`;
   - either appends immediate `run/wake`, or inserts `run_waits` and changes jobs to `WAITING`.

2. `emit_event`
   - creates/locks an event sentinel;
   - appends canonical `event/emit`;
   - changes the event row from non-emitted to emitted using a payload-NULL fence;
   - appends one `run/wake` per active waiter;
   - changes matching jobs from `WAITING` to `PENDING`;
   - deletes resolved active waits.

3. `run_state`
   - remains read-only; only its fold logic changes.

4. `get_schema_version`
   - returns `p03` when `0003` is the last file.

P03 does not alter P01 or P02 function definitions other than `run_state`, which P03 explicitly owns as the projection extension point.

### Transformation boundaries

| Boundary | Source | Transformation | Destination |
|---|---|---|---|
| Await request | token, run ID, await ID, scoped event key, deadline/UI metadata | validation, event lock, claim fence | log + active wait + jobs |
| Event emission | scoped event key and JSONB payload | event serialization and first-write fence | canonical event log pointer |
| Wake fan-out | active waits for event key | per-run status/await-ID revalidation | wake log + `PENDING` jobs |
| Immediate resolution | emitted event row | dereference canonical event log row | await/wake pair + returned payload |
| State projection | ordered run log | latest-await matching by await ID | `awaiting` or `in-progress` |
| Resume | `PENDING` jobs row | existing P01 claim protocol | new `RUNNING` token |

### Why this is a targeted change

P01 already reserves the scheduler states and enforces claim-field consistency. P02 already reserves all required event kinds and supplies the append monopoly. The apply tool already supports `0003`. The missing behavior is localized to two side tables, two verbs, and one projection replacement. Refactoring jobs, log writers, the apply CLI, or plugin metadata would duplicate existing responsibilities and widen the ABI unnecessarily.

## Resolved decisions

| # | Decision | Evidence and rationale | Rejected alternative |
|---:|---|---|---|
| 1 | `run_events` has a nullable `payload` cache plus canonical log pointer. SQL `NULL` means not emitted; JSON `null` is emitted. | D3 requires log SoT but explicitly preserves the `WHERE payload IS NULL` first-write fence. The cache is used only for state/fencing; immediate consumers dereference the `event/emit` log row. | Log-only lookup without a row-level fence: it complicates serialization and does not satisfy the required payload-NULL implementation note. Payload-as-SoT is also rejected. |
| 2 | Global lock order is **event row → jobs row(s), ordered by run_id → wait row**. Await uses `FOR SHARE` on the event row; emit uses `FOR UPDATE`. Fan-out `run_id` order is for deterministic wake order (tests), not to prevent emit/emit inversion. | D3 and the Absurd comparison require event-before-run. The wait row is locked only after its jobs row so duplicate/timeout paths cannot form a jobs↔wait cycle. Same-key emits serialize on the event row `FOR UPDATE`; different-key waiter sets are disjoint because `run_waits_pkey` is `run_id`. Deadlock-freedom vs a claim-fenced writer in the same session: see Component 7. | Jobs-first locking, which deadlocks with emit’s event-first fan-out. Advisory locks are rejected because the event sentinel provides a collision-free row lock. |
| 3 | One active wait per `run_id`; `run_waits` primary key is `run_id`, and `await_id` is globally unique while active. | `jobs.run_id` is unique and one jobs row can have only one scheduler state. A run cannot be `WAITING` on two independent event keys at once. | `(run_id, step_name)` upsert, which permits multiple registrations that one jobs row cannot represent and retargets waits silently. |
| 4 | Emission fans out to every matching active wait. | Absurd wakes all matching waits, and D3 does not define consume-once semantics. Persistent events also make later waits resolve immediately. | Consume-once delivery, which would make the first waiter hide the event from others and conflict with emit-before-wait persistence. |
| 5 | Emit-before-wait appends both `run/await` and `run/wake` in the waiting run’s log, but does not insert `run_waits` or release the claim. | F §7 says resolve immediately with no yield; the pair makes replay/folding use the same shape as a suspended/resumed wait. | Skipping both log rows, which would make the continuation payload invisible to replay; appending only `run/wake`, which loses the await identity. |
| 6 | `run_state()` adds `awaiting` when the latest `run/await` lacks a later same-`await_id` `run/wake`. Precedence is `final` → `error` → `awaiting` → `in-progress`. | P02 explicitly leaves awaiting to P03. The fold remains log-only and does not depend on missing jobs terminal-log bridging. | Reading `jobs.status`, which would make scheduler state a second historical truth. |
| 7 | P03 implements event await only. It stores a nullable deadline but performs no deadline scan or sleep transition. | Parent P04 owns `SLEEPING`, timeout ticking, retry, and backoff. | A generic wait/sleep function in P03, which would partially implement P04’s state machine. |
| 8 | `emit_event` appends canonical `event/emit`; the kernel function then appends each `run/wake`. | F §7 distinguishes emitter intent from kernel wake production. Both still call the P02 writer. | Letting callers append `run/wake`, which bypasses side-table/status fencing and the write monopoly. |
| 9 | Public verbs are `await_event(uuid,text,text,text,uuid,timestamptz,jsonb,integer)` and `emit_event(text,text,jsonb)`. Await returns accepted/suspend/payload/source metadata; emit returns first-write/wake-count/source metadata. | The wait path needs a claim token and explicit run ID like `emit_step_claimed`; the emitter has no claim token. Parameter errors raise; lost claim returns an accepted=false row. | A single overloaded function or token-bearing emitter; both obscure authority boundaries. Boolean-only await is rejected because immediate resolution must return payload. |
| 10 | `0003` replaces the version body with `p03`; `0006` continues to win on the full tree. | Numeric apply order and the existing source-tree contract. | Expecting `p03` from full-tree tests, which would ignore `0006`. |
| 11 | Wake updates only a jobs row that is still `WAITING` and still has the matching wait row/await ID; it does not use `emit_step_claimed`. | A waiting job has no live token. The side registration plus status is the wake fence, and the existing PENDING-only index serves the result. | Manufacturing a claim token or changing `claim_job` to claim WAITING directly. |
| 12 | Suspended wait does **not** write `jobs.available_at`. Deadline lives only on `run_waits.deadline` (and the `run/await` payload). Wake sets `available_at` to the emit timestamp. | Mid-flow checkpoint: `claim_job` is PENDING-only, so `available_at` on `WAITING` is inert in P03. Putting `COALESCE(deadline, infinity)` on the jobs row would leak P04’s sleep clock into wait. F §7 only requires `available_at=now()` on wake. | Stashing deadline on `jobs.available_at` while `WAITING`; setting `available_at=now()` at wait time. |

### `cordis.run_events`

**Kind:** persistent kernel side table  
**Lifecycle:** one immutable logical event record per `(event_scope_id, event_name)`; the row begins as a sentinel and may transition once to emitted  
**Historical authority:** none; canonical payload is the pointed-to `event/emit` log row

#### Exact columns

| Column | Type | Null/default | Meaning |
|---|---|---|---|
| `event_scope_id` | `text` | `NOT NULL` | Opaque capability scope |
| `event_name` | `text` | `NOT NULL` | Name within scope |
| `event_log_run_id` | `text` | `NOT NULL DEFAULT '@event/' || pg_catalog.gen_random_uuid()::text` | Internal log stream containing the canonical `event/emit` |
| `payload` | `jsonb` | nullable | First-write fence/cache; SQL `NULL` means not emitted |
| `emit_seq` | `bigint` | nullable | `agent_steps.seq` of canonical `event/emit` in `event_log_run_id` |
| `created_at` | `timestamptz` | `NOT NULL DEFAULT pg_catalog.clock_timestamp()` | Sentinel creation time |
| `emitted_at` | `timestamptz` | nullable | First successful emit time |

`@event/<uuid>` is an internal log-stream namespace. It is not a jobs row, a second queue, or an `agent_runs` registry. It exists because emit-before-wait needs a canonical log record even when no waiting run exists. The function-generated UUID and unique constraint prevent two event keys from sharing that stream.

#### Named constraints

| Name | Exact contract |
|---|---|
| `run_events_pkey` | `PRIMARY KEY (event_scope_id, event_name)` |
| `run_events_event_log_run_id_key` | `UNIQUE (event_log_run_id)` |
| `run_events_scope_nonblank_check` | `CHECK (pg_catalog.btrim(event_scope_id) <> '')` |
| `run_events_name_nonblank_check` | `CHECK (pg_catalog.btrim(event_name) <> '')` |
| `run_events_event_log_run_id_check` | `CHECK (event_log_run_id ~ '^@event/[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$')` |
| `run_events_emit_seq_check` | `CHECK (emit_seq IS NULL OR emit_seq > 0)` |
| `run_events_emission_state_check` | exactly one of: all `payload`, `emit_seq`, `emitted_at` are SQL NULL; or all three are non-NULL |

The emission-state predicate must be logically equivalent to:

```text
(payload IS NULL AND emit_seq IS NULL AND emitted_at IS NULL)
OR
(payload IS NOT NULL AND emit_seq IS NOT NULL AND emitted_at IS NOT NULL)
```

JSONB `null` satisfies `payload IS NOT NULL` and therefore represents a committed event.

`emit_event` must update the sentinel with a predicate containing:

```text
WHERE payload IS NULL
```

That predicate is the first-write fence required by D3.

No foreign key from `run_events` to `agent_steps`. A composite FK `(event_log_run_id, emit_seq) REFERENCES cordis.agent_steps(run_id, seq)` is technically legal (`agent_steps_pkey`; `MATCH SIMPLE` would skip sentinel rows with `emit_seq IS NULL`). The function validates that the pointed row exists and has the expected kind/key whenever it dereferences an emitted event.

## Component 3 — Event payload schemas

All P03 log calls pass `step_name = NULL`.

### `event/emit`

Stored in the internal `event_log_run_id` stream:

```json
{
  "event_scope_id": "<opaque scope>",
  "event_name": "<name>",
  "payload": "<arbitrary JSON value>"
}
```

`payload` may be any JSONB type, including JSON `null`. SQL `NULL` is rejected at the function boundary.

The `agent_steps` row is canonical. `run_events.payload` is a cache/fence and must not be preferred over the log when returning an event to an await caller.

### `run/await`

Stored in the waiting run:

```json
{
  "await_id": "<UUID string>",
  "event_scope_id": "<opaque scope>",
  "event_name": "<name>",
  "deadline": "<jsonb timestamptz or null>",
  "ui_metadata": {}
}
```

Serialize `deadline` with `pg_catalog.to_jsonb(p_deadline)` so SQL NULL becomes JSON `null` and a present timestamp is ISO-8601-with-offset. Do not concatenate `::text`. `ui_metadata` must be a JSON object. P03 does not interpret it. P04 will read this field and `run_waits.deadline`.

### `run/wake`

Stored in the waiting run:

```json
{
  "await_id": "<UUID string>",
  "event_scope_id": "<opaque scope>",
  "event_name": "<name>",
  "source_run_id": "@event/<uuid>",
  "source_seq": 123
}
```

Both source fields are required because `agent_steps` is keyed by `(run_id, seq)`. The wake row does not duplicate the event payload. Resume projections dereference the canonical `event/emit` row.

## Component 4 — `cordis.await_event`

### Interface

```text
cordis.await_event(
    p_claim_token    uuid,
    p_run_id         text,
    p_event_scope_id text,
    p_event_name     text,
    p_await_id       uuid,
    p_deadline       timestamptz DEFAULT NULL,
    p_ui_metadata    jsonb DEFAULT '{}'::jsonb,
    p_extend_seconds integer DEFAULT 90
) RETURNS TABLE (
    accepted          boolean,
    should_suspend    boolean,
    payload           jsonb,
    source_run_id     text,
    source_seq        bigint
)
```

Catalog identity:

```text
cordis.await_event(uuid,text,text,text,uuid,timestamp with time zone,jsonb,integer)
```

The function always returns exactly one row when it does not raise.

Return meanings:

| Situation | `accepted` | `should_suspend` | Other fields |
|---|---:|---:|---|
| Lost/missing/expired/non-running/mismatched claim | false | false | all null |
| Event not emitted; wait committed by caller | true | true | payload/source null |
| Event already emitted | true | false | canonical payload and source pointer |

### Validation and raise-vs-false order

Validate before any mutation:

- `p_run_id` non-null and nonblank;
- event scope/name non-null and nonblank;
- `p_await_id` non-null;
- `p_ui_metadata` non-null and a JSON object;
- `p_extend_seconds > 0`.

`p_deadline` is stored as given: past timestamps and `±infinity` are accepted. P03 does not tick deadlines and does not raise on those values. P04 must define timeout semantics for them.

Malformed inputs raise `invalid_parameter_value`.

After parameter validation:

- null token returns the lost-claim row;
- unknown token, wrong run, non-`RUNNING`, or expired lease returns the same lost-claim row;
- no log, wait, jobs, or lasting sentinel mutation may remain on a lost-claim return.

If the function inserted a new event sentinel before discovering that the claim was lost, it must remove that still-unemitted sentinel before returning false. Existing sentinels are left unchanged. Because the sentinel is locked and the current transaction created it, this cleanup cannot remove another transaction’s event or wait.

### Global lock sequence

1. Insert event sentinel with `ON CONFLICT DO NOTHING`; remember whether this transaction inserted it.
2. Lock the event row `FOR SHARE`.
3. Capture `pg_catalog.clock_timestamp()`.
4. Acquire the jobs row with `SELECT … FOR UPDATE SKIP LOCKED` using the live-claim predicate (`claim_token`, `run_id`, `status='RUNNING'`, unexpired). If the row is missing **or already locked**, raise a private SQLSTATE inside an inner PL/pgSQL block so the subtransaction rolls back: that drops any sentinel this statement inserted and **releases the event-row lock before `await_event` returns**. Then return `accepted=false`. Do not wait on the jobs row while holding the event lock, and do not leave the event lock held in the caller’s open transaction.
5. Apply the `GREATEST` lease extension on the locked `job_id`.
6. `SELECT … FOR UPDATE` any existing `run_waits` row for this `run_id` only after the jobs lock succeeded.
7. Run duplicate-wait checks, then log/side/status mutations.

No jobs lock is acquired before the event row. `SKIP LOCKED` is required so a transaction that already holds the same `RUNNING` row (P02 `emit_step_claimed` / `checkpoint`, then `emit_event`) cannot deadlock with `await_event`’s event-then-jobs order.

### Duplicate-wait checks

These checks run on **both** the suspended and immediate branches, after a successful jobs UPDATE and **before any** `emit_step`:

- an existing `run_waits` row for that run is an invariant violation and raises `object_not_in_prerequisite_state`;
- await-id reuse in this run’s log raises `invalid_parameter_value` when:

  ```sql
  EXISTS (
    SELECT 1 FROM cordis.agent_steps
     WHERE run_id = p_run_id
       AND kind = 'run/await'
       AND payload->>'await_id' = p_await_id::text
  )
  ```

  Prefix scan on `agent_steps_pkey (run_id, seq)`. Do not scan `run/wake` or the whole table.
- the function never upserts or retargets an existing wait.

`await_id` uniqueness is **not** global across runs. `run_waits_await_id_key` only covers active wait rows. After a wait is deleted, another run may reuse the same UUID. Tests must not assert global uniqueness of historical `await_id` values. `run_state` matching is per-run and is unaffected.

Normal response-retry behavior is not an exception:

- after a committed suspended wait, the old token is cleared, so a duplicate call with that token returns `accepted=false` without another log row;
- a second call in the same transaction after the first has set `WAITING` likewise returns false (jobs UPDATE matches zero rows);
- after wake and re-claim, callers must use a new `await_id` **for that same run**; reuse of the old ID in that run’s log raises.

### Pre-await lease handling

With the jobs row locked and still live, extend:

```text
claim_expires_at =
  GREATEST(existing expiry, captured time + p_extend_seconds)
```

This extension occurs before appending `run/await`.

- It never shortens a longer lease.
- In the suspended branch it is immediately replaced with SQL NULL when the claim is cleared.
- In the immediate branch it remains as the retained live lease.
- Any later failure rolls it back with all other statement effects.

### Suspended-wait sequence

When `run_events.payload IS NULL`:

1. Validate and lock as above (event SHARE, fenced jobs UPDATE with GREATEST).
2. Duplicate-wait checks (existing `run_waits` row; same-run `await_id` reuse) before any log append.
3. Append `run/await` through `cordis.emit_step`; capture `await_seq`.
4. Insert exactly one `run_waits` row with that `await_seq`.
5. Update the locked jobs row:
   - `status = 'WAITING'`;
   - `available_at` is **not assigned** (left at its pre-wait value; P03 does not use it as a deadline clock);
   - `claim_token = NULL`;
   - `claimed_by = NULL`;
   - `claim_expires_at = NULL`;
   - `completed_at = NULL`;
   - `result = NULL`;
   - `error = NULL`.
6. Require exactly one jobs row to be updated. An impossible zero-row result raises `object_not_in_prerequisite_state` so the log and registration roll back.
7. Return accepted=true, should_suspend=true.
8. The caller commits or rolls back; the function never commits.

The order after fencing is strictly:

```text
run/await log
→ run_waits insert
→ jobs WAITING / ownership cleared
```

### Immediate-resolve sequence

When `run_events.payload IS NOT NULL`:

1. Validate and lock as above (event SHARE, fenced jobs UPDATE with GREATEST).
2. Duplicate-wait checks (existing `run_waits` row; same-run `await_id` reuse) before any log append. Immediate resolve must raise on `await_id` reuse so a second call cannot append another await/wake pair.
3. Require non-null `emit_seq` and `emitted_at`.
4. Load `cordis.agent_steps(event_log_run_id, emit_seq)`.
5. Require:
   - row exists;
   - kind is `event/emit`;
   - payload scope/name match the event row.
6. Read the returned payload from that canonical log row, not from `run_events.payload`.
7. Append `run/await`; capture its sequence. The live lease was already extended by the fenced jobs UPDATE; do not shorten or reset it here.
8. Append `run/wake` with the event source pointer.
9. Do not insert `run_waits`.
10. Do not change jobs status, token, claimed worker, or attempt.
11. Return accepted=true, should_suspend=false, canonical payload and source pointer.

The `run/await`/`run/wake` pair commits atomically. If either append fails, neither row and no lease extension commit.

## Component 5 — `cordis.emit_event`

### Interface

```text
cordis.emit_event(
    p_event_scope_id text,
    p_event_name     text,
    p_payload        jsonb
) RETURNS TABLE (
    emitted       boolean,
    woken_count   integer,
    source_run_id text,
    source_seq    bigint
)
```

Catalog identity:

```text
cordis.emit_event(text,text,jsonb)
```

The function always returns exactly one row when it does not raise.

Return meanings:

| Situation | `emitted` | `woken_count` | Source pointer |
|---|---:|---:|---|
| First committed emission | true | number of active waits resolved | new canonical pointer |
| Duplicate emission | false | 0 | original canonical pointer |

Duplicate emit does not compare payloads and does not reveal the original payload. First write always wins, even if the repeated payload happens to be equal.

### Validation

Raise `invalid_parameter_value` before mutation for:

- null/blank scope;
- null/blank name;
- SQL NULL payload.

JSONB `null` is valid and counts as emitted.

P03 performs no grant lookup. P07/P08 must later authorize the exact event key before calling or exposing this verb.

### Lock and first-write sequence

1. Insert a sentinel event row if absent.
2. Lock it `FOR UPDATE`.
3. If `payload IS NOT NULL`:
   - return emitted=false, wake count 0, existing source pointer;
   - append no log rows;
   - perform no wake side effects.
4. Capture `clock_timestamp()`.
5. Append canonical `event/emit` through `cordis.emit_step` using `event_log_run_id`; capture `emit_seq`.
6. Update the locked event row with:
   - `payload = p_payload`;
   - `emit_seq = captured sequence`;
   - `emitted_at = captured time`;
   - event-key predicate;
   - `AND payload IS NULL`.
7. Require exactly one updated row. Zero rows raises `object_not_in_prerequisite_state`, rolling back the log append.
8. Enumerate matching active waits ordered by `run_id`.
9. Resolve each as described below.
10. Return emitted=true, total successfully resolved waits, and source pointer.

The event log append precedes the side-table cache update, but both are invisible until the same transaction commits. The event row lock establishes the winner before the append; the `payload IS NULL` update is the explicit first-write fence.

### Fan-out sequence per waiter

For each candidate `run_waits` row, in ascending `run_id` order:

1. Lock its `cordis.jobs` row `FOR UPDATE`.
2. Lock the `run_waits` row after the jobs row.
3. Revalidate:
   - wait event key still matches;
   - `await_id` still matches the candidate;
   - jobs status is exactly `WAITING`;
   - all jobs claim fields are null.
4. If the row is missing or inconsistent, raise `object_not_in_prerequisite_state`. Do not silently skip it, because a committed event would otherwise make the wait permanently unwakeable.
5. Append `run/wake` through `cordis.emit_step`.
6. Update jobs:
   - `status = 'PENDING'`;
   - `available_at = emitted time`;
   - claim fields remain null;
   - `completed_at = NULL`;
   - `result = NULL`;
   - `error = NULL`.
7. Guard the update with `run_id` and `status='WAITING'`; require one row.
8. Delete `run_waits` using both `run_id` and `await_id`; require one row.
9. Increment `woken_count`.

The complete fan-out is one transaction. An error on any waiter rolls back:

- the canonical `event/emit`;
- the event fence/cache;
- every prior `run/wake`;
- every jobs transition;
- every wait deletion.

This all-or-nothing behavior avoids partially committing one logical first emission.

### Deadline behavior in P03

P03 does not exclude a wait whose deadline is in the past. Until P04 installs timeout resolution, an active wait remains event-resolvable regardless of deadline. P04 must choose the winner by using the same event → jobs → wait lock order and by fencing on `WAITING + await_id`; it must not add a second resolution mechanism.

## Component 6 — `cordis.run_state` projection

### Interface compatibility

Before and after P03, the signature remains:

```text
cordis.run_state(text)
RETURNS TABLE (
    status text,
    steps_used integer,
    answer text,
    error text
)
```

Volatility remains `STABLE`; security remains invoker; the function remains log-only.

Calling `run_state('@event/<uuid>')` on an internal event stream is not a product API. That stream contains only `event/emit` rows, so the fold reports `in-progress` with `steps_used = 0`. Workers must fold the waiting run, then follow `source_run_id`/`source_seq` to read payload. README should say the `@event/` prefix is a kernel stream namespace, not a job.

### Status fold

For one run:

1. If any `final` exists, status is `final`.
2. Else if any `error` exists, status is `error`.
3. Else find the latest `run/await` by descending `seq`.
4. If no await exists, status is `in-progress`.
5. If an await exists, read its string `await_id`.
6. Find a later `run/wake` in the same run where:
   - wake `seq` is greater than await `seq`;
   - wake payload’s `await_id` equals the latest await’s ID.
7. If no matching wake exists, status is `awaiting`.
8. Otherwise status is `in-progress`.

Existing `steps_used`, answer extraction, error extraction, and final-over-error behavior remain unchanged.

This deliberately ignores:

- `jobs.status`;
- `run_waits`;
- event cache state;
- the missing P01 jobs-terminal-to-log bridge.

An immediate resolve produces adjacent await/wake rows and therefore never projects as awaiting after commit.

## Component 7 — Concurrency and lifecycle

### Global lock order

Every P03 and future P04 resolution path must use:

```text
1. run_events row for (event_scope_id, event_name)
2. cordis.jobs rows in ascending run_id order
3. corresponding run_waits row
4. append-only log writes and side/status updates
```

Mode differences:

- await: event row `FOR SHARE`;
- emit: event row `FOR UPDATE`;
- future timeout: same event row before jobs, using a mode that excludes concurrent emit resolution.

The wait path inserts a new wait only after locking jobs; it never locks an existing wait first. Emit reads candidate IDs without locking wait rows, then locks jobs before locking each registration.

### Wait versus emit interleavings

#### Wait wins the event lock first

```text
await: event SHARE → jobs lock → await log → wait row → WAITING
emit: blocks on event UPDATE
await commits
emit acquires event → sees committed wait → wake → PENDING
```

No wake is missed.

#### Emit wins the event lock first

```text
emit: event UPDATE → event/emit → no current wait → commit
await: acquires event SHARE → sees emitted pointer
      → await + wake pair → remains RUNNING
```

No wait row is created.

#### Why there is no deadlock

Await and emit, used alone, never hold a jobs row while waiting for an event row.

A later worker may, in **one transaction**, call `emit_step_claimed` / `checkpoint` (which holds its own `RUNNING` jobs row) and then `emit_event` (which waits for an event row). That is a jobs→event edge. A concurrent `await_event` on the same token takes the event row first. If that await **blocked** on the jobs row, the two would deadlock (event vs jobs inversion).

`await_event` therefore acquires the jobs row with `FOR UPDATE SKIP LOCKED`. If the claim-held writer already owns the row, the inner block raises SQLSTATE `P0301`, the subtransaction rolls back (sentinel + event `FOR SHARE` gone), and the function returns `accepted=false` without holding those locks in the caller’s still-open transaction. `emit_event` can then proceed. Callers retry await on the next claim. PostgreSQL row locks last until transaction end unless a subtransaction rolls them back; statement return is not enough.

Emit’s fan-out still only `FOR UPDATE`s `WAITING` rows. A claim-fenced writer can only hold a `RUNNING` row (`jobs_claim_fields_check`). Those sets remain disjoint, so fan-out cannot close a cycle with a claim-held writer.

P03 **allows** `emit_event` in a transaction that already holds a claim-fenced `RUNNING` lock. Do not forbid that combination; P05/P17 will need it.

Fan-out still walks matching waiters by ascending `run_id` so wake order is deterministic and tests can assert it. Same-key emits already serialize on the event row; different-key waiter sets are disjoint (`run_waits_pkey` is `run_id`), so emit/emit jobs-lock inversion does not occur.

No advisory runtime lock is needed.

### Transaction and process model

All functions are synchronous PostgreSQL functions in the caller’s transaction.

P03 creates no:

- background worker;
- timer;
- event loop;
- polling loop;
- connection affinity;
- notification dependency;
- cancellation task.

If the caller aborts or disconnects before commit, PostgreSQL rolls back the complete wait or emit operation.

### Resource lifecycle

- Non-emitted event sentinels persist once a valid wait commits.
- Emitted event rows persist indefinitely in P03.
- Active wait rows exist only while the scheduler row is `WAITING`.
- Waking deletes the active wait but preserves all log history.
- Event/log retention is unassigned and must be handled by a later migration without treating side tables as history.

## State and data flow

### Suspended await

Trigger: a worker with a live claim calls `await_event` for an un-emitted key.

```text
worker inputs
  → scalar validation
  → event sentinel insertion/SHARE lock
  → jobs token/run/status lock
  → wall-clock lease validation
  → non-shortening lease extension
  → emit_step(run/await)
  → run_waits registration
  → jobs RUNNING → WAITING
  → clear token/worker/expiry
  → caller COMMIT
```

Observation after commit:

- log contains `run/await`;
- `run_waits` contains one row;
- jobs is `WAITING`;
- claim fields are null;
- `run_state` is `awaiting`;
- `claim_job` returns no row.

Out-of-order visibility is prevented by the transaction. Other sessions see either the prior live `RUNNING` state or the complete committed waiting state.

### First emit with active waits

Trigger: UI/callback invokes `emit_event`.

```text
event inputs
  → scalar validation
  → event UPDATE lock
  → emit_step(event/emit) in internal event stream
  → payload/emit_seq/emitted_at fence update
  → active waits ordered by run_id
      → jobs lock
      → wait lock + revalidation
      → emit_step(run/wake)
      → jobs WAITING → PENDING
      → delete active wait
  → caller COMMIT
```

Observation after commit:

- event row is emitted;
- canonical event log row exists;
- every matched run has `run/wake`;
- every matched job is due `PENDING`;
- active waits are gone;
- `run_state` returns `in-progress`;
- normal P01 claim can resume each job.

### Emit-before-wait

Trigger: emit commits before any wait exists.

```text
emit_event
  → event/emit + emitted fence, wake count 0

later await_event
  → sees emitted event
  → reads canonical payload from source log
  → appends run/await + run/wake
  → keeps job RUNNING and token live
  → returns payload directly
```

No scheduler yield occurs.

### Duplicate emit

Trigger: any later call for the same key.

```text
event UPDATE lock
  → payload already non-NULL
  → return emitted=false, wake count 0, original pointer
```

No log or scheduler mutation occurs. Future waiters resolve themselves through the immediate branch.

### Resume

Trigger: worker polls/targets a job woken to `PENDING`.

```text
claim_job
  → existing P01 PENDING-only index and token minting
  → RUNNING with a new claim token
  → consumer reads latest run/await + matching run/wake
  → follows source pointer to event/emit payload
```

The old pre-wait token can never mutate the row because it was cleared.

## Errors and edge cases

### Parameter errors: raise

`await_event` raises `invalid_parameter_value` for:

- null/blank run ID;
- null/blank scope or name;
- null await ID;
- SQL NULL UI metadata;
- non-object UI metadata;
- non-positive lease extension;
- reuse of a prior committed await ID under a new live claim.

`emit_event` raises `invalid_parameter_value` for:

- null/blank scope or name;
- SQL NULL payload.

Malformed parameters raise before ownership is classified as lost.

### Lost claim: return accepted=false

After valid scalar parameters, `await_event` returns:

```text
accepted=false
should_suspend=false
payload/source fields=NULL
```

for:

- null token;
- unknown token;
- token belonging to another run;
- non-`RUNNING` row;
- expired lease;
- token cleared by yield, completion, failure, stale-reap, or an earlier wait.

No log, wait, jobs, or lasting newly-created sentinel change may remain.

### Duplicate wait

Defined behavior:

1. First call commits a suspended wait.
2. Repeating with the old token returns accepted=false because the jobs row is no longer `RUNNING`.
3. Repeating inside the same transaction after the first call has changed the row to `WAITING` also returns accepted=false.
4. Calling with a new claim but reusing the old `await_id` raises `invalid_parameter_value`.
5. An unexpected active `run_waits` row under a valid `RUNNING` claim raises `object_not_in_prerequisite_state`.
6. The function never updates an existing wait to another event key.

Thus duplicate wait is neither an upsert nor a second active registration.

### Duplicate emit

- First transaction to update `payload IS NULL` wins.
- Later calls return emitted=false.
- The original payload, source stream, source sequence, and timestamp remain unchanged.
- Duplicate emit appends neither `event/emit` nor `run/wake`.
- JSON `null` is an emitted value and therefore also blocks later emit.

### Emit-before-wait

- Event remains persisted.
- Later await appends both await and wake.
- No `run_waits` row exists.
- Jobs remains `RUNNING`.
- Claim token remains valid and is extended without shortening.
- Payload is read from canonical `event/emit`, not trusted from the side cache.

### Fan-out

- All currently committed matching waits wake.
- Nonmatching scopes with the same event name do not wake.
- Nonmatching names within the same scope do not wake.
- Later waits also resolve immediately because the event persists.
- Wake order is deterministic by `run_id`.
- One invalid matching registration aborts the entire first emit; partial fan-out is forbidden.

### Lost claim while entering wait

- If the lease has expired before the jobs lock/time check, await returns false and appends nothing.
- Once the row is locked and confirmed live, the function extends the lease before appending.
- Stale-reap cannot update that row while await holds the jobs lock.
- The suspended branch then clears the lease atomically.
- A function error rolls back the temporary extension and every subsequent mutation.

### Lease expiry while `WAITING`

A committed waiting row has:

```text
status = WAITING
claim_token = NULL
claimed_by = NULL
claim_expires_at = NULL
```

Therefore:

- `release_stale` does not select it;
- `claim_job` does not select it;
- passing wall-clock time alone does not change it in P03;
- event emission still wakes it;
- P04 will later own deadline resolution.

This proves the system still uses one jobs queue: no waiter is claimed from a side table.

### Wait versus emit deadlock

The only two valid race outcomes are:

- wait commits first, then emit wakes it;
- emit commits first, then wait immediately resolves.

Neither path holds jobs while requesting the event row, so no event/jobs lock cycle exists. Tests must enforce a finite statement timeout so a regression becomes a failure rather than a hung suite.

### Event-cache corruption or missing source row

If an emitted event row points to no matching canonical `event/emit`, immediate await raises `object_not_in_prerequisite_state` and leaves the claim/log unchanged.

The cache is not trusted for returned payload. If the cache differs from the canonical log due to out-of-band mutation, immediate await returns the log payload. P03 does not add ACL enforcement; P07 must prevent untrusted direct side-table mutation.

### Wait-row/jobs inconsistency during emit

A matching wait whose jobs row is not `WAITING`, or whose await ID/key changed, is an invariant error. First emit rolls back instead of committing an event that can no longer resolve that wait.

### Empty collection

First emit with no active waiters succeeds:

```text
emitted=true
woken_count=0
```

The event remains available to later immediate waits.

### Transaction interruption

- Await rollback restores the original `RUNNING` claim and removes its await log/registration.
- Emit rollback leaves the event un-emitted and all jobs/waits unchanged.
- PostgreSQL sequence gaps caused by rolled-back log inserts are accepted, as in P02.
- There is no cancellation API within P03.

## Risks and migration

### New persistent side tables

There is no existing `cordis.run_waits` or `cordis.run_events` data to migrate. P03 must not import Absurd or pg-agent rows.

`CREATE TABLE IF NOT EXISTS` permits replay but does not reconcile an incompatible manually-created table. Apply must fail rather than drop or rewrite such a table.

### New observable `run_state` label

Callers that previously assumed the closed set `final|error|in-progress` must accept `awaiting`. This is the intended P03 API expansion. The signature and other fields do not change.

### Internal event log stream namespace

Canonical event emissions use generated `@event/<uuid>` log stream IDs because an event can be emitted before any waiting run exists. This is a storage namespace only and has no jobs row. UUID collision is practically negligible and event rows additionally enforce uniqueness.

Future producer validation should reserve the `@event/` prefix for kernel streams. P03 does not modify the existing broad `jobs.run_id` text constraint.

### Side cache and permission boundary

`run_events.payload` is a first-write fence but remains directly mutable by the install role until P07 establishes permissions. Kernel functions treat the log pointer as canonical. P03 must not claim ACL-level tamper resistance before P07.

### Event retention

Events persist and make every later same-key wait immediately resolve. P03 has no consume/delete/TTL policy. Reusing event keys for logically distinct operations is a caller error; callers must use opaque scopes or unique names appropriate to their capability.

A later retention migration must not delete canonical log history or reinterpret the cache as truth.

### Deadline without timeout worker

Before P04, a deadline is descriptive only. A wait does not wake merely because its deadline passes. This is deliberate phase ordering, not a hidden polling requirement.

Until P04, a `WAITING` run is unreachable to every product verb: `complete_claim` / `fail_claim` / `yield_claim` / `renew_claim` require a live `RUNNING` token, and `release_stale` only reaps `RUNNING`. The only recovery is `emit_event` on the exact key (or out-of-band SQL). Tests and operators must not expect `fail_claim` to unstick a waiter.

### All-or-nothing fan-out cost

`emit_event` performs O(W) jobs locks and log appends for W active waiters, in deterministic order. This favors correctness and atomic first emission over very large fan-out throughput. No batching/partial-commit policy is introduced in P03.

### Existing jobs-to-terminal-log gap

P03 does not repair `complete_claim`, `fail_claim`, or `release_stale` logging. `run_state` remains log-derived, so a jobs row may be terminal while the log remains in-progress or awaiting if callers bypass the expected log writer. This pre-existing gap is outside P03.

### Rollback

Applying an older source tree over a P03 database is unsupported. Use `--reset` on disposable databases to test older trees.

A failed `0003` apply rolls back its tables, functions, and `p03` marker with the tree transaction. The target database itself may remain, following the existing apply contract.

### Concurrency test shape

Use `psql_session` for the transaction that must hold locks. Use the existing one-shot `psql` in a thread for the blocked operation. Set a finite PostgreSQL `statement_timeout`, not `pg_sleep`.

Interleaving A:

1. Session A begins and executes suspended await but does not commit.
2. Session B starts emit and blocks on the event row.
3. Session A commits.
4. Session B completes with one wake.
5. Final state is emitted, PENDING, no active wait.

Interleaving B:

1. Session A begins, executes emit, and leaves the transaction uncommitted.
2. Session B starts await and blocks on the event row.
3. Session A commits.
4. Session B completes immediate resolution.
5. Final state is RUNNING with the original token and no active wait.
