# P01 — `cordis.jobs` Upgrade and Dual-Locus Claim Protocol

Date: 2026-08-23  
Status: **ready to implement**

## Summary

P01 adds the first runtime table to the canonical `zcordis-pgembed/sql/` tree: schema-qualified `cordis.jobs`, with one durable scheduler row per logical `run_id`, lease ownership fields, eligibility timestamps, and terminal result/error fields. It introduces only the primitive SQL claim verbs — claim, renew/heartbeat, yield, complete, fail, and stale-reap — so an in-DB worker and a future host worker use the same database ABI. Claims use `FOR UPDATE SKIP LOCKED`. Ownership is fenced by a server-generated `claim_token` plus an unexpired `claim_expires_at`. Stale leases are requeued before each claim. P01 does not implement log events, wait/event tables, sleep/retry policy, handler dispatch, a worker loop, a plugin catalog, or a host SDK. The apply CLI stays unchanged. P00 tests that encode an empty kernel are retargeted to the current `0000+0001` tree without weakening source-tree validation.

## Goal

Implement the P01 contract from `docs/plans/2026-08-23-pg-cordis-development.md:105-111`:

- Create `cordis.jobs`, not `public.jobs` and not an `absurd` schema.
- Keep one logical queue.
- Make the jobs row the sole authoritative claim locus, keyed by `run_id`.
- Provide the same SQL verbs for in-DB and host workers.
- Ensure two connections cannot claim the same eligible job concurrently.
- Ensure a yielded job with the same `run_id` can be claimed again by another connection.
- Reap expired `RUNNING` leases before selecting a new job.
- Keep P01 limited to jobs-row mutation.

### Protocol (F) that P01 implements

`docs/analysis/2026-08-23-f-yield-loop-protocol-sketch.md` is protocol, not product SQL (`:1-3`, `:280-287` leave exact DDL open).

Jobs-row contract (F §2.2, `:47-62`): `job_id`; `run_id` NOT NULL for agent work; status set including illustrative `WAITING`/`SLEEPING`; claim fields `claim_token`, `claimed_by`, `claim_expires_at`, `attempt`; wake column `available_at`; payload JSONB (`step_cursor` is cache, not SoT). Invariant: at most one non-terminal jobs row per `run_id` (`:59-60`). Do not accumulate one job per step.

Fencing (F §2.4, `:78-86`): `UPDATE … WHERE claim_token = $token AND claim_expires_at > now()`; 0 rows ⇒ lost ownership, stop without appending. P01 evaluates the deadline with `clock_timestamp()` (see Design).

Verbs both loci speak (F §3, `:91-104`): `claim`, `heartbeat`, `yield`, `complete`, `fail`, `release_stale`. Out of P01: `checkpoint` (P02), `wait` (P03), `sleep` (P04). Claim SELECT in the sketch includes WAITING/SLEEPING when due; P01 claim selects **PENDING only** until P03/P04 define those transitions.

Stale reap first (F §8, `:214-223`): RUNNING ∧ `claim_expires_at ≤ now()` → PENDING, `available_at=now()`, new attempt, fence old token. Log event `run/claim_timeout` is P02. Lease opinion (`:224`): lease ≥ HTTP timeout + heartbeat slack; pg-agent curlopt is 90s.

State machine P01 implements (F §11, `:262-272`):

```text
PENDING  --claim--> RUNNING
RUNNING  --yield--> PENDING
RUNNING  --complete--> DONE
RUNNING  --fail--> ERROR
RUNNING  --lease expire--> PENDING
```

Dual locus (F §9, `:227-241`): host uses the **same SQL verbs** over libpq. Replacing session-pinning `rlm_loop` is P05/P09, not P01.

## Current data/control flow

Before P01:

```text
apply_pg_cordis.py
  → discover 0000_kernel.sql
  → create/use target database
  → one transaction + advisory lock
  → schema cordis + get_schema_version()
```

No product jobs table, no claim operation.

After P01:

```text
producer (future enqueue, or P01 tests INSERT)
  → one cordis.jobs row per run_id
  → PENDING, available_at ≤ current time

worker connection
  → cordis.claim_job(...)
      → bounded stale-reap of expired RUNNING
      → SELECT eligible PENDING FOR UPDATE SKIP LOCKED
      → UPDATE RUNNING + new claim_token + expiry
      → return claimed row
  → COMMIT claim transaction

worker performs work **outside** the claim transaction

worker connection
  → cordis.renew_claim(token, ...)
  → or cordis.yield_claim(token)
  → or cordis.complete_claim(token, result)
  → or cordis.fail_claim(token, reason)
  → COMMIT transition

another worker
  → cordis.claim_job(...)
```

The claim transaction must be short. P01 functions do not commit for the caller. A caller must commit a successful claim before long-running work; otherwise row locks block others.

## Mutation points

1. `claim_job`: requeue expired `RUNNING`; change one eligible row to `RUNNING`; mint token and lease.
2. `release_stale`: expired `RUNNING` → `PENDING`; increment `attempt`; clear ownership.
3. `renew_claim`: reset lease horizon for the live token.
4. `yield_claim`: `RUNNING` → immediately eligible `PENDING`; clear ownership.
5. `complete_claim`: `RUNNING` → `DONE`; store result; clear ownership.
6. `fail_claim`: `RUNNING` → terminal `ERROR`; store structured reason; clear ownership.

No P01 function writes `agent_steps`, `agent_runs`, `run_waits`, `run_events`, audit tables, or handler tables.

### Loader compatibility

P01 verbs are plpgsql. The landed preflight cannot accept them as-is.

`FORBIDDEN_STMTS` includes (`tools/apply_pg_cordis.py:31-34`):

```text
(?:^|;\s*)(BEGIN|COMMIT|ROLLBACK|END|START TRANSACTION)\s*;
```

with `re.I | re.M`. `END;` is in the list because PostgreSQL treats `END` as a `COMMIT` synonym. Under multiline mode, a function body’s line-start `END;` matches. `strip_sql_comments` (`:83-90`) only removes `--` and `/* */`; it does not strip `$tag$ … $tag$` bodies, so the function text is scanned.

**W09 change (minimal):** before running `FORBIDDEN_STMTS`, replace dollar-quoted spans with spaces:

```text
\$([A-Za-z0-9_]*)\$.*?\$\1\$   (DOTALL)
```

Keep comment stripping. Keep the existing keyword list, including `END`. Meta-command rejection stays line-based on the raw file (`preflight_sql` `:93-99`).

Still rejected (exit 2, no database mutation):

- top-level `BEGIN;` / `COMMIT;` / `ROLLBACK;` / `END;` / `START TRANSACTION;`
- `CREATE DATABASE`, `GRANT`, `CREATE EXTENSION`, `CREATE TABLE public.*`, `CREATE SCHEMA absurd`, etc.

Now accepted:

- `CREATE FUNCTION … LANGUAGE plpgsql AS $fn$ BEGIN … END; $fn$;`
- dollar-quoted strings that happen to contain `BEGIN;`

Rejected alternative: require authors to write `END` without a semicolon before `$$`. That would leave every later Px one typo away from a false preflight failure.

Do not otherwise refactor discovery, apply, `verify_bootstrap`, or pgembed.

pgembed bundles PostgreSQL 18.4 (`pgembed/pgbuild/Makefile:53`). `pg_catalog.gen_random_uuid()` is built-in (≥13). P01 must not `CREATE EXTENSION pgcrypto`.

### Time source

Use `clock_timestamp()`, not `now()`.

- `now()` is transaction-start time and stays stale in a long transaction.
- `clock_timestamp()` is wall-clock at the operation boundary (G sketch and scratch driver).
- Each mutating operation should capture one wall-clock value for its predicate and timestamp assignments where practical.

Fence (conceptually):

```text
claim_token = supplied_token
AND status = 'RUNNING'
AND claim_expires_at > current wall-clock time
```

A zero-row update means lost ownership. The predicate must be on the mutating `UPDATE`, not a preliminary `SELECT` (TOCTOU).

### Function packaging

All P01 verbs:

- `LANGUAGE plpgsql`
- `VOLATILE`
- `SECURITY INVOKER` (same as `sql/0000_kernel.sql:9-11`)
- bodies reference `cordis.jobs` and `pg_catalog.gen_random_uuid()` / `pg_catalog.clock_timestamp()`; never depend on caller `search_path`
- no `GRANT` in this file (P07)

`get_schema_version` replacement keeps `LANGUAGE sql IMMUTABLE SECURITY INVOKER` and zero-argument `RETURNS text`.

### Status set and invariants

Text `CHECK`, not a PostgreSQL enum (enum `ALTER` is hostile to numbered-file replay):

```text
PENDING | RUNNING | WAITING | SLEEPING | DONE | ERROR
```

Names are uppercase to match pg-agent morphology.

P01 actively implements only:

```text
PENDING  --claim-->  RUNNING
RUNNING  --yield-->  PENDING
RUNNING  --complete--> DONE
RUNNING  --fail--> ERROR
RUNNING  --lease expires--> PENDING
```

`WAITING`/`SLEEPING` are reserved. P01 never creates them and never claims them. P03 owns wait/event; P04 owns sleep/retry and may replace the claim eligibility body later.

Constraints:

1. `status` ∈ the six values.
2. `attempt >= 1`.
3. Claim fields present **exactly** when `RUNNING`:

   ```text
   status = RUNNING
   ↔ claim_token IS NOT NULL
      AND claimed_by IS NOT NULL
      AND claim_expires_at IS NOT NULL
   ```

4. `claimed_by`, when present, must not be empty after trimming whitespace.
5. Terminal status and completion timestamp agree:

   ```text
   status IN (DONE, ERROR) ↔ completed_at IS NOT NULL
   ```

   All non-terminal states have `completed_at IS NULL`.

The table does **not** require `claim_expires_at` to be in the future; an expired `RUNNING` row is valid stale-reap input.

Name every table constraint so catalog tests and later numbered files can `DROP CONSTRAINT IF EXISTS` / `ADD CONSTRAINT` without guessing `pg_constraint.conname`:

| Name | Kind |
|---|---|
| `jobs_pkey` | `PRIMARY KEY (job_id)` |
| `jobs_run_id_key` | `UNIQUE (run_id)` |
| `jobs_claim_token_key` | `UNIQUE (claim_token)` |
| `jobs_status_check` | status ∈ six values |
| `jobs_attempt_check` | `attempt >= 1` |
| `jobs_claim_fields_check` | claim columns present iff `RUNNING` |
| `jobs_claimed_by_nonblank_check` | non-null `claimed_by` is non-blank after trim |
| `jobs_terminal_time_check` | `DONE`/`ERROR` iff `completed_at IS NOT NULL` |

Cancel is **not** a P01 status or verb (D4 five-piece has no cancel). The named CHECK is the replay-safe extension point if a later item adds `CANCELLED` or a force-fail path. Do not add `CANCELLED` now.

### Uniqueness and indexes

- PK `jobs_pkey` on `job_id`
- `jobs_run_id_key` `UNIQUE (run_id)`
- `jobs_claim_token_key` `UNIQUE (claim_token)` — multiple NULLs are allowed; a non-null token identifies at most one row

Partial indexes (**must** use `CREATE INDEX IF NOT EXISTS`; a bare `CREATE INDEX` fails the second in-place apply and rolls back the tree):

```text
CREATE INDEX IF NOT EXISTS jobs_ready_idx
ON cordis.jobs (priority DESC, available_at ASC, job_id ASC)
WHERE status = 'PENDING'

CREATE INDEX IF NOT EXISTS jobs_stale_claim_idx
ON cordis.jobs (claim_expires_at ASC, job_id ASC)
WHERE status = 'RUNNING'
```

`available_at = '-infinity'` makes an ordinary inserted `PENDING` row immediately eligible. Yield and stale-reap set `available_at` to the captured wall clock.

### Persistence and replay

`CREATE TABLE IF NOT EXISTS`. The numbered file must not drop columns, drop constraints, or rebuild an incompatible pre-existing table.

- Fresh P00 database: create table and indexes.
- Second in-place apply: table/index/function statements succeed; existing job rows remain.
- `--reset`: database recreation drops all rows.
- Older source tree onto a P01 database: unsupported downgrade; `--reset` on a disposable database.
- A P01 SQL failure rolls back schema, table, indexes, functions, and version marker together (one apply transaction).

## Component 2 — Claim and stale-reap verbs

### `cordis.release_stale`

```text
cordis.release_stale(
    p_run_id text DEFAULT NULL,
    p_limit  integer DEFAULT 100
) RETURNS integer
```

Return value: number of rows moved from expired `RUNNING` to `PENDING`.

Inputs:

- `p_run_id = NULL`: sweep any run.
- Non-null `p_run_id`: that logical run only.
- `p_limit`: positive maximum. A targeted run can affect at most one row because `run_id` is unique.

Reject: empty/whitespace-only non-null `p_run_id`; `p_limit <= 0`.

Algorithm:

1. Capture wall-clock `t0` with `clock_timestamp()`.
2. Select up to `p_limit` rows: `status = 'RUNNING'` AND `claim_expires_at <= t0` AND optional `run_id` filter.
3. Order `claim_expires_at ASC, job_id ASC`.
4. `FOR UPDATE SKIP LOCKED`.
5. Update selected rows: `status = 'PENDING'`; `available_at = t0`; `attempt = attempt + 1`; `claim_token`, `claimed_by`, `claim_expires_at` = NULL; `completed_at`, `result`, `error` = NULL.
6. Return affected-row count.

No `run/claim_timeout` log write (P02). P02 may later wrap this function while preserving the jobs-row transition.

If `attempt` would overflow `integer`, fail with PostgreSQL’s numeric-range error rather than wrap; the row stays unchanged because the function is transactional.

The default bound of 100 prevents one claim call from rewriting an unbounded stale backlog. Repeated claims eventually sweep it. An expired row not selected in one sweep remains fenced (`RUNNING` with expired token) and cannot be claimed until a later sweep. A targeted `p_run_id` processes only that row.

### `cordis.claim_job`

```text
cordis.claim_job(
    p_run_id        text,
    p_worker_id     text,
    p_lease_seconds integer DEFAULT 90
) RETURNS SETOF cordis.jobs
```

Returns zero or one row. `p_run_id` is nullable:

- `NULL` — next eligible job from the queue;
- non-null — only that `run_id`.

The returned row contains the generated `claim_token`. The worker must retain it for later mutating verbs.

Validate (raise invalid-parameter, not `false`):

- `p_worker_id` null or blank;
- `p_run_id` non-null and blank;
- `p_lease_seconds <= 0`.

No P01 maximum lease. Future worker policy may add an upper bound; the primitive only requires a positive duration.

Algorithm:

1. `PERFORM cordis.release_stale(p_run_id, 100)`.
2. Capture a fresh wall-clock timestamp after reap.
3. Select one row: `status = 'PENDING'` AND `available_at <= t` AND optional `run_id = p_run_id`.
4. Order `priority DESC, available_at ASC, job_id ASC`.
5. `FOR UPDATE SKIP LOCKED`.
6. Atomically update: `status = 'RUNNING'`; `claim_token = pg_catalog.gen_random_uuid()`; `claimed_by = p_worker_id`; `claim_expires_at = t + make_interval(secs => p_lease_seconds)` (integer seconds cannot be added to `timestamptz` directly); `completed_at`, `result`, `error` = NULL.
7. Return the updated row.

Candidate select and update must be one statement or one transaction with no unlock gap. Do not “select, commit, then update.”

P01 claim predicate considers only `PENDING`. `WAITING`/`SLEEPING` pass the status CHECK but are not selected until P03/P04.

Empty queue: return zero rows (not an exception). A live `RUNNING` targeted `run_id` also returns zero rows. `DONE`/`ERROR`/`WAITING`/`SLEEPING` are not eligible in P01. Future `available_at` is not eligible.

Concurrency: two `claim_job(NULL, …)` on the same ready row — first locks and updates; second `SKIP LOCKED` skips it and returns zero rows or another ready job. After the first commits, the row is `RUNNING` and no longer eligible. Two targeted claims for the same `run_id`: at most one returns the row.

Token is generated by PostgreSQL, not supplied by the worker.

## Component 3 — Lease renewal and owner transitions

Shared fence on every token verb (part of the `UPDATE`, not a prior `SELECT`):

```text
claim_token = p_claim_token
AND status = 'RUNNING'
AND claim_expires_at > clock_timestamp()
```

All token verbs return `boolean`:

- `true` — caller owned a live claim and the transition occurred;
- `false` — token null, unknown, cleared, expired, or not `RUNNING`.

`false` must not raise an ownership exception and must not mutate the row. The worker treats `false` as `lost_claim` and stops claim-owned work.

### `cordis.renew_claim`

```text
cordis.renew_claim(
    p_claim_token    uuid,
    p_extend_seconds integer DEFAULT 90
) RETURNS boolean
```

- Validate `p_extend_seconds > 0`.
- Live token: `claim_expires_at = current wall-clock + make_interval(secs => p_extend_seconds)`.
- **Do not add** the duration to the old expiry (prevents unbounded accumulation).
- Preserve status, run identity, worker identity, attempt, payload, and timestamps other than expiry.
- Return `false` if not live.

This is the canonical heartbeat ABI. Do **not** add a second `heartbeat_claim` alias in P01.

90s is a protocol baseline, not a guarantee that every external operation fits. A worker whose HTTP exceeds 90s must pass a longer lease or renew in flight. P05 owns LLM-call behavior.

### `cordis.yield_claim`

```text
cordis.yield_claim(p_claim_token uuid) RETURNS boolean
```

Live token → `status = 'PENDING'`; `available_at = current wall-clock`; claim fields NULL; `completed_at`/`result`/`error` NULL. Preserve `job_id`, `run_id`, `job_type`, `payload`, `priority`, `attempt`, `created_at`.

Yield does **not** increment `attempt` (normal continuation, not recovery). No P01 log write; P02 may add optional `run/yield` later.

### `cordis.complete_claim`

```text
cordis.complete_claim(
    p_claim_token uuid,
    p_result      jsonb DEFAULT NULL
) RETURNS boolean
```

Live token → `status = 'DONE'`; `result = p_result`; `error = NULL`; `completed_at = now`; claim fields NULL. Do not change `run_id`, `payload`, `attempt`, or `created_at`.

SQL `NULL` result is allowed (handlers with no payload). A second complete with the old token returns `false` (token already cleared). Callers that need “did the first complete commit?” read the row by `run_id`.

### `cordis.fail_claim`

```text
cordis.fail_claim(
    p_claim_token uuid,
    p_reason      jsonb
) RETURNS boolean
```

`p_reason` must not be SQL `NULL` (JSONB object or scalar is allowed). Live token → `status = 'ERROR'`; `error = p_reason`; `result = NULL`; `completed_at = now`; claim fields NULL.

P01 **always** produces terminal `ERROR`. No requeue-on-fail, backoff, max-attempt, or dead-letter. P04 owns that policy and may later revise this verb while retaining token fencing.

### Lost claim during work

```text
renew / transition returns false
    → lost_claim
    → stop work owned by that claim
    → do not append a P01 log event
    → do not issue another jobs mutation using the old token
```

P01 cannot roll back an external side effect performed before the token was discovered stale. D2/P16 define non-transactional tool recovery. P01 only guarantees that subsequent jobs-row mutations with the old token are fenced.

## Component 5 — State and data flow

### Enqueue to pending

P01 does not ship an enqueue function (mid-flow: no thin `enqueue_job`). Tests `INSERT` fixtures. Future P05/P09 or another trusted producer inserts one row: unique `run_id`, `job_type`, `payload`, `PENDING`, `available_at` immediate or future, `attempt = 1`, claim fields NULL. A continuation updates the existing scheduler row through the verbs. Duplicate `run_id` fails on `UNIQUE (run_id)`.

### Claim / yield-reclaim / stale / terminal

```text
claim_job(... worker A ...)
  → RUNNING, token A

yield_claim(token A)  -- commit
  → PENDING, available_at = now, token cleared, attempt unchanged

claim_job(... worker B ...)
  → same job_id/run_id RUNNING, token B ≠ token A

RUNNING + expired token A
  → release_stale → PENDING, attempt+1, token cleared
  → claim_job may claim in the same transaction → token B
  → later token-A mutations affect 0 rows

RUNNING + live token → complete_claim → DONE + result + completed_at
RUNNING + live token → fail_claim    → ERROR + error + completed_at
```

Terminal rows remain the one scheduler handle. They are not a history of step attempts.

### Observation and transaction boundaries

No `LISTEN/NOTIFY`, callback, or published property. Observe by selecting `cordis.jobs` or consuming the returned claim row.

Each SQL function runs in the **caller’s** transaction:

- claim and stale-reap are atomic together;
- renew / yield / complete / fail are one atomic update each;
- the caller must commit a successful transition for another connection to observe it.

`claimed_by` is descriptive worker identity, not session affinity (D1: a later worker may use another backend).

### Out-of-order / duplicate / dropped operations

| Situation | Required result |
|---|---|
| Two claims for one pending row | Exactly one returns the row; the other skips it |
| Duplicate claim after a live claim | Zero rows for that run |
| Yield twice with same token | First `true`; second `false` |
| Complete/fail after yield | `false`; token was cleared |
| Renew after expiry | `false`; reaper or another claimant may win |
| Old worker after stale-reap | `false`; old token cannot mutate |
| Transition response dropped | Caller reads by `run_id`; cleared token cannot duplicate the transition |
| Claim transaction rolled back | Row stays in prior visible state; generated token discarded |
| Yield transaction rolled back | Row stays `RUNNING`; original token remains until expiry or a valid transition |

## Component 6 — Concurrency and lifecycle

P01 is database-transactional and synchronous at the SQL function boundary. It does not create a background worker, thread, async task, timer, or connection pool. The claim is not tied to the PostgreSQL backend after commit.

Locking:

- Candidate selection: `FOR UPDATE SKIP LOCKED`.
- Stale-reap: same, on expired rows, before update.
- Token transitions: fenced `UPDATE` predicate.
- No advisory lock for runtime claiming. The apply CLI advisory lock only serializes schema application.

Lease:

- Default 90s. Expiry is wall-clock. PostgreSQL does **not** kill the worker when the lease expires.
- A worker that continues after expiry may still perform external work, but cannot commit a token-protected jobs mutation.
- Recovery is the next `claim_job` or explicit `release_stale`. P01 does not install a timer.

Renew vs stale-reap race: whichever `UPDATE` wins; the loser’s token predicate fails. Two claimers: `SKIP LOCKED` avoids blocking on an already-selected candidate.

## Component 7 — Error handling and edge cases

### Parameter errors (raise)

- blank worker ID
- blank targeted run ID
- non-positive lease duration
- non-positive stale-reap limit
- null failure reason

These are caller contract errors, not lost-claim.

### Lost ownership (return `false`)

- null token; nonexistent token; token of another job; row not `RUNNING`; expired token; token cleared by yield/complete/fail/stale-reap

Do not retry the same token. Start a new claim cycle.

### Missing or terminal job (`claim_job` → zero rows)

Empty queue; targeted `run_id` missing; targeted row `RUNNING` with live lease; `DONE`/`ERROR`/`WAITING`/`SLEEPING`; `available_at` in the future.

### Invalid direct inserts (table constraints reject)

Unknown status; `attempt < 1`; `RUNNING` without all claim fields; non-`RUNNING` with any claim field; terminal without `completed_at`; non-terminal with `completed_at`; duplicate `run_id`; duplicate non-null `claim_token`.

P01 tests may INSERT fixtures. Production callers should use future enqueue and the verbs rather than bypassing the protocol.

### Empty payload/result

- `payload` cannot be SQL `NULL`; default `{}`.
- `complete_claim` accepts SQL `NULL` result.
- `fail_claim` rejects SQL `NULL` reason; JSON `null` as a JSONB value is allowed if intentional.
- Empty `job_type` strings are not rejected in P01; handler validation is P06/P09.

### Lease expiry during external work

1. Worker must stop before another claim-owned mutation.
2. `release_stale` or a later `claim_job` may requeue.
3. Next worker gets a new token and incremented `attempt`.
4. P01 does not decide whether the external work is safe to repeat (P02/P05/P16).

# Risks and migration

- **No data migration from pg-agent.** There is no product `jobs` table before P01. `public.jobs` lives in another database. Scratch `ALTER TABLE jobs ADD COLUMN` is not a migration source.
- **Version marker.** Identity stays stable; returned string `p00` → `p01`. Loader remains compatible. An older checkout with only `0000` against a P01 database is an unsupported downgrade; `--reset` on a disposable DB.
- **Global `run_id` uniqueness.** Terminal rows remain the live scheduler record. Deliberate: no one-job-per-step accumulation, no terminal claim history in the queue. If retention needs history, archive outside `cordis.jobs`; do not weaken P01 to a partial unique index without revisiting the one-queue invariant.
- **Reserved statuses without transitions.** P01 never creates `WAITING`/`SLEEPING` and does not claim them. Direct callers must not use them as a P03/P04 substitute. P03/P04 must update the claim body atomically when they land.
- **Cancel is unassigned.** There is no `PENDING → terminal` edge and no force-stop of a live claim. D4’s five-piece has no cancel; P01 does not add `CANCELLED`. A later item that needs it must `DROP CONSTRAINT IF EXISTS jobs_status_check` / `ADD CONSTRAINT` in a new numbered file — that is why the CHECK is named. Do not treat `fail_claim` after a courtesy claim as the product cancel API.
- **Lease vs HTTP.** A 90s HTTP without renewal can lose the lease at the boundary. P05/P10 must request a longer lease or renew in flight. P01 must not hold a transaction across external I/O.
- **No GRANTs.** Install role can mutate `cordis.jobs` until P07. Do not add ad hoc grants P07 would undo.
- **Token fencing is not external exactly-once.** It cannot undo a file edit or HTTP already performed. D2/P16 owns effect classification.
- **Apply vs runtime rollback.** Failed apply rolls back the whole tree transaction. Failed runtime verb rolls back that caller transaction only. Tests must keep distinguishing DB creation (outside apply txn) from schema creation (inside), as `test_sql_failure_rolls_back_tree` already does.
