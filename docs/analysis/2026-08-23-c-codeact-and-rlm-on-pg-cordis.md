# C — CodeAct and RLM on pg_cordis

Date: 2026-08-23 · Series: sequential research A→I · Status: **analysis evidence.** Decisions and working hypotheses: `2026-08-23-i-architecture-snapshot.md`. CodeAct primary, RLM complementary; spawn is D9 (always enqueue).

Evidence base (read-only): `pg-agent` v1 + v2 — the only repo where both paradigms already run in-database (`v2/pg_agent_rlm.sql` opens "RLM × CodeAct"); `deepseek-harness` `packages/core/agent-loop/` (`ReactLoopAgent` and the `AgentLoop` service); the RLM paper `zcordis-pgembed/docs/RECURSIVE LANGUAGE MODELS.md`. Inherits A/B findings; does not reopen them.

The governing requirement for C, restated: pg_cordis must run **two** agent paradigms — **CodeAct** and **RLM** — with the shared-substrate vs paradigm-specific split made explicit across **log, plugins, projections, env/REPL**. The paper defines both paradigms and the discriminator between them: a CodeAct agent "can execute code inside of a ReAct (Yao et al., 2023) loop. Unlike an RLM, it does not offload its prompt to the code environment, and instead provides it directly to the LM" (§2.2); an RLM "treats prompts as part of the environment. It loads the input prompt as a variable inside a Python REPL environment" (Figure 2). One line: **CodeAct gives the context to the model; RLM puts the context where the model can address it.**

---

**Key tradeoffs at a glance** (full analysis in the tradeoffs section):

- **TC1** — Loop locus: kernel SQL function vs plugin behind a loop seam vs kernel substrate + paradigm as data-driven policy bundle.
- **TC2** — Spawn model: synchronous in-transaction recursion vs async job-queue children vs mixed with a threshold.
- **TC3** — Env/REPL state: log-derived projection vs separate run-scoped workspace vs a declared third state tier.
- **TC4** — Event vocabulary: one paradigm-neutral log vs per-paradigm logs vs shared envelope + paradigm-scoped kinds.
- **TC5** — CodeAct action surface: single-tool SQL JSON action vs free-form in-database code execution vs structured tool-call blocks.
- **TC6** — Prompt assembly: loop-internal fold vs registered deterministic-fold projection consumed by loops.

---

## CodeAct paradigm on pg_cordis

### The two existing instantiations (evidence)

**pg-agent: SQL-native CodeAct.** The CodeAct loop is `agent_run(question, max_steps)` in `v2/pg_agent_functional.sql` (identical shape in `v1/pg_agent_functional.sql` at lines 134/192/402: `make_system_prompt`, `fold_messages`, `agent_run`). Its system prompt hands the model exactly one tool — "唯一工具是 execute_sql" (`make_system_prompt`) — and a strict JSON reply contract `{thought, action: execute_sql|null, action_input, final_answer}` parsed by `parse_llm_output` into the `llm_decision` type. The action executes through `exec_sql_readonly`: single statement only, a keyword blacklist (`drop`/`insert`/`set`/… ), wrapped as `SELECT COALESCE(jsonb_agg(t),'[]') FROM (<stmt> LIMIT n) t`. The loop body itself is four moves — fold history → `sql_retry('http_call_llm(jsonb)', msgs, 2)` → parse → route (`final` vs action) → `emit_step` — matching the file's architecture mantra "决策是纯函数，动作是薄外壳，编排是数据，注册是注释" (decisions are pure functions, actions are thin shells, orchestration is data, registration is comments). Two hardenings exist on this base: the `data_analysis` paradigm (`v2/pg_agent_data_analysis.sql`) enforces code-XOR-final_answer in `make_da_prompt` **plus a runtime query latch** — `rlm_loop` refuses a final answer until at least one SELECT succeeded (`v_got_q`, the "必须先成功执行至少一条 SELECT 才能 final_answer" branch) and wraps failures in structured `Type/Phase/Problem/Solution` coaching (`da_wrap_obs`); and `agent_run_hybrid` (`v2/pg_agent_rlm.sql`) adds `action = 'rlm'` so a CodeAct run can delegate a subtask to an RLM child. Note the parser already unifies dialects: `parse_rlm_output` maps ReAct-style `action_input` onto `code` whenever `action ∈ ('execute_sql','eval','ipython','sql')` — action-JSON and code converge at the parse layer.

**DSH: the tool-calling loop (CodeAct-family baseline).** `ReactLoopAgent` (`packages/core/agent-loop/src/agent.ts`) is strictly a function-calling ReAct loop — tool calls are structured blocks in assistant messages, executed by `executeToolCalls` in parallel-safe groups capped by `maxParallelToolCalls` (`DEFAULT_MAX_PARALLEL_TOOL_CALLS = 10`, `src/constants.ts`; the cap is settings-owned and read through at each group boundary per `src/index.ts`). Its module doc states the load-bearing property: "Every request is derived from the session log" — each step rebuilds the request from `session.deriveMessages()`, logs `request/header` + `request/context` on change, streams `assistant/chunk` events (with `chunkSeqs`), and finalizes `assistant/message` with usage, `sourceEventSeqs`, and an `interrupted` marker. Plugins interpose at `agent/pre-step` (reject or rewrite a step) and `agent/request` (propose the LLM config) waterfalls; humans interpose via `send`/`followup`/`steer`/`inject` with `next-turn`/`next-step` inbox targeting, `cancel`, and the `idle|maintenance|running` phase machine. It is not code-action — but it is the loop DSH would extend toward CodeAct, and everything structural (turn/step enclosure, log-derived requests, interruption semantics) transfers to pg_cordis unchanged.

### What CodeAct becomes on pg_cordis (opinions)

- **The action is SQL that runs where the data lives.** `exec_sql_readonly` executes the model's statement as a query plan against the same database that holds the log, the plugin registry, and the data — no serialization boundary between agent and substrate. Tools are SQL functions: `render_workbench_tools()` (`v2/pg_agent_workbench_core.sql`, STABLE, read-only, `read_only` before `temp_view_mutation`, stable text when the registry is empty) renders the compiled COMMENT registry into the prompt — `da_system_prompt()` is literally `make_da_prompt(...) || render_workbench_tools()`, and workbench tools deliberately bypass `jobs`/`worker()`/`job_handler` (file header, lines 7–16). This answers A's open question directly: **yes, prompt-side tool injection from the compiled registry is the pattern, and it generalizes to both paradigms** — CodeAct invokes tools as discrete actions; RLM composes several inside one statement ("可用 WITH 在一条语句里组合多个调用", `make_rlm_prompt` rule 5).
- **Parallel tool calls invert.** DSH parallelizes calls across a step (cap 10); the SQL paradigm serializes actions but gains intra-action parallelism — one `WITH` composing several workbench functions is planned and executed as one tree. This is a genuine database-unique term for the CodeAct contract (picked up in TC5).
- **Gaps pg_cordis must close** (analysis, not design): (1) *capability scoping* — the keyword blacklist cannot stop side-effecting `VOLATILE` functions reachable from a plain `SELECT`; the real boundary must be role/RLS/`search_path` discipline (feeds Topic D); (2) *interruption and steering* — a PL/pgSQL loop has no `AbortController`; DSH's cancel/steer/inject and aborted-turn semantics need a transaction/session-level counterpart (statement timeouts, cancel keys, or host-mediated step boundaries); (3) *streaming* — `http_call_llm` is a blocking request; DSH's chunk-level replay fidelity has no in-database analog yet.

## RLM paradigm on pg_cordis

### Paper → pg-agent lineage (evidence)

The paper's mechanics, as verified in `docs/RECURSIVE LANGUAGE MODELS.md`: the context is loaded as a variable in a REPL; the REPL also exposes "`llm_query`", a function to "query an LLM (that can handle around 500K chars) inside your REPL environment" (Appendix D.1); observations are truncated by design — "You will only be able to see truncated outputs from the REPL environment" (D.1) — and the §3.1 trajectory patterns are exactly three: "Filtering input information using code execution based on model priors", "Chunking and recursively sub-calling LMs", and "Passing recursive LM outputs through variables for long output tasks" (RLMs "produce essentially unbounded tokens well beyond the limit of the base LM"). Observation 1: RLMs "scale to the 10M+ token regime" — on BrowseComp+ (GPT-5), RLM 91.33% vs CodeAct+BM25 51.00%, at an average $0.99. Observation 2: the REPL alone handles long inputs; recursive sub-calling wins on information-dense ones. Two implementation pains the paper names itself: "RLMs without asynchronous LM calls are slow. We implemented all sub-LM queries naively as blocking / sequential calls" (§A), and final-answer detection is brittle — the `FINAL()`/`FINALVAR()` tag strategy (§A, D.1). The experiments use only one level of recursion (sub-calls are plain LMs) and defer deeper recursion to future work (§5).

pg-agent implements this in three deliberate stages:

1. **v1 standalone** (`v1/pg_agent_rlm.sql`): own tables `rlm_runs`/`rlm_steps`/`rlm_vars`/`rlm_children`; the header states the three principles against the paper — prompt-as-a-variable (context into `rlm_vars`, never the system prompt), a persistent SQL REPL (the model's only action is one SELECT), recursive sub-agents as function calls — with the mantra "上下文是变量，工具是 SQL，子 agent 是函数" (context is a variable, tools are SQL, sub-agents are functions). `rlm_steps` has a first-class `'spawn'` kind.
2. **v1 integrated** (`v1/pg_agent_rlm_integrated.sql`): merges into `agent_runs`/`agent_steps` — the header enumerates the shared base: one run table extended with `paradigm`/`parent_run_id`/`depth`, one append log for which "run_state() 对两种范式都成立" (the fold holds for both paradigms), one queue (`job_type='rlm_run'`), one `http_call_llm`/`exec_sql_readonly`. Cross-paradigm spawning works in both directions (`agent_run_hybrid` action=rlm; `codeact_spawn` from RLM — v1's depending on `pg_agent_poml.sql`'s `agent_loop` per that header, v2's calling `agent_run` directly).
3. **v2** (`v2/pg_agent_rlm.sql`): one loop body — "rlm_loop 按 agent_runs.paradigm 分支" (prompt and query-latch selection branch on the paradigm column); `rlm_children` gains `kind 'rlm'|'codeact'`; both paradigms' runs share one table by design ("两种范式的 run 在同一张表", usage examples).

REPL mechanics: `rlm_vars(run_id, name, value jsonb)` plus `env_keys/get/set/set_text/set_json/len/peek/search/chunk`; run binding through the session GUC `rlm.run_id` (`rlm_bind`/`rlm_current_run`; `rlm_eval` saves and restores the binding around child evaluation); prompt-shrinking (`make_rlm_user`: questions over 1500 chars live only in the env); observation discipline (`rlm_clip` at 4000 chars with the full result stored in env `last_obs` — the paper's truncated-output rule as data).

Recursion mechanics: `rlm_spawn` is **synchronous and in-transaction** (child `agent_runs` row, `depth+1`, caps: `depth ≥ max_depth` or ≥ 4 hard, ≤ 16 children per parent, child `max_steps = LEAST(parent, 6)`); `rlm_map` fans out ≤ 8 chunks; `rlm_list` reads the ledger. `codeact_spawn` calls `agent_run` and then discovers its child by `ORDER BY created_at DESC LIMIT 1` before retro-linking `parent_run_id` — a race-prone heuristic, not a contract.

### RLM on pg_cordis (opinions)

- **The REPL is tables.** Durable, queryable, transactional variables; the paper's unbounded-output-by-variables becomes jsonb columns; `llm_query` is `http_call_llm`; sub-agents are runs in the same log with lineage (`parent_run_id`, `rlm_children`). `env_search`/`env_chunk` are the paper's filtering pattern in embryo — pgembed's retrieval substrate upgrades them from regex over one variable to fused recall over projections (B's retrieval tier).
- **Postgres answers one of the paper's two pains and already hardens the other.** Blocking sub-calls: PG has a native async path — the same `jobs`/`worker()` queue the loops already register on (`h_rlm_run`, `h_hybrid_run` via `COMMENT '{"job_handler":…}'`) — at the price of losing run-tree atomicity (TC2). Termination brittleness: pg-agent's JSON protocol with code-XOR-final_answer plus the runtime query latch is structurally stronger than `FINAL()` tags.
- **In-run compaction mostly dissolves for RLM** (opinion): the context never enters the window, so the pressure compaction addresses moves out of the loop. CodeAct turn history still grows, so compaction remains a paradigm-agnostic log-layer concern (B's `surfaceOp` brackets) — answering B's compaction question: **plugin category, not loop-internal** (DSH's `packages/compaction/` already is one).

## Shared substrate vs paradigm-specific

The split, explicit — every row cites the precedent that already implements it:

| Layer | Shared substrate (both paradigms use it today) | Paradigm-specific |
|---|---|---|
| Run registry | `agent_runs` + `paradigm` discriminator (`'codeact'|'rlm'|'hybrid'|'data_analysis'`), `parent_run_id`/`depth`/`max_depth` (v1-integrated header, v2) | budget policy — max_steps/rows/depth propagation rules (`LEAST(parent,6)`, hard 4) |
| Step log | `agent_steps` append-only (`llm/tool/final/error`), `emit_step()` the only writer, `run_state()` fold valid for both paradigms | spawn lineage events — v1 had a `'spawn'` kind; v2's `fold_rlm_messages` still understands it but nothing emits it (a gap, TC2/TC4) |
| LLM transport | `http_call_llm` + `sql_retry` (both loops, same GUC config, `response_format json_object`) | none observed |
| Execution shell | `exec_sql_readonly` + `da_*` helpers | observation policy — `rlm_clip`+`last_obs` vs raw `obs::text` |
| Prompt assembly | fold over the log (`fold_messages` / `fold_rlm_messages` — same IMMUTABLE shape) | system prompt, decision type + parser (`llm_decision` vs `rlm_decision`), fold policy (clipping, spawn kinds) |
| Tool registry | workbench COMMENT contract + `render_workbench_tools()` into the prompt (`da_system_prompt`) | invocation style — discrete action vs composed inside one SELECT/WITH |
| Env/REPL | `rlm_vars` + `env_*` (RLM owns; hybrid borrows for `question`/`context`) | REPL API surface; prompt-shrinking rules |
| Scheduling | `jobs`/`handlers`/`worker()`; the loops themselves are registered handlers (`h_agent_run`, `h_rlm_run`, `h_hybrid_run`) | spawn model (TC2) |
| Projections | `run_state()`, folds (B's deterministic tier) | per-paradigm folds (TC6) |

Two independent designs converge on the same conclusion: pg-agent v2 runs **one loop body branched by paradigm** (prompt + latch selection via the `paradigm` column), and DSH runs **one loop class consuming seams** — `AgentLoop extends Service implements AgentFactory` with `static inject = ['agents','sessions','llm','tools','systemPrompt']`, registering itself via `ctx.agents.setFactory(this)` ("Concrete agent-loop plugin: creates scoped ReactLoopAgents, publishes them through the agent/session registries", `src/index.ts`). *Opinion*: make the convergence explicit in pg_cordis — a small shared **loop kernel** (transport, append, fold, budget, spawn plumbing, tool rendering) plus **a paradigm as a policy bundle** (prompt + parser + action router + env policy + observation policy) expressed as registry data — the same single-metadata-with-discriminator move A's T7 opinion made for invocation models. This answers A's "loop plugin or kernel?": the kernel is substrate; the paradigm is a plugin over it; pg-agent hardcoding `rlm_loop` in SQL is an accident of v2 iteration, already half-corrected by the job-handler registration.

Answers to B's C-questions (opinions): **prompt assembly is a projection** — `fold_*` are already pure IMMUTABLE functions over the log; CodeAct and RLM need different folds over the *same* log (different policy, not different events). **One shared log with a paradigm discriminator**, not per-paradigm logs (consistent with B's TB1(c)); run registry metadata carries the discriminator, mirroring A's T7. The **multi-writer append policy is a log-layer property, hence paradigm-independent** — serialized append transactions per session (advisory lock or seq-PK contention) — but its ownership interacts with isolation, so it is restated as a D question below.

## Key tradeoffs (opinion, not decision)

Analyzed in turn; each ends with an opinion. None is a decision; A's SQL-first hypothesis and B's log/projection contract are assumed, not reopened.

**TC1 — Loop locus.** Options: (a) kernel SQL functions (pg-agent today); (b) a loop seam with loop plugins (DSH's `agents`/`AgentFactory`); (c) kernel substrate + paradigms as data-driven policy bundles. Analysis: (a) is proven but every new paradigm edits the kernel and the fold; (b) is DSH-proven but assumes the TypeScript runtime A ruled out as the authoring surface; (c) is what both precedents are drifting toward — v2's paradigm branching is (c) with the policy table inlined in one function, and DSH's seam consumption is (c) with the policy encoded in injectable services — and it matches A T2's "metadata complete from day one, enforcement progressive". *Opinion: (c). The loop kernel is the only part that must be SQL; a paradigm registers like any other plugin (A's contract) and the kernel dispatches on its policy bundle.*

**TC2 — Spawn model.** Options: (a) synchronous in-transaction recursion (`rlm_spawn` today): the entire run tree commits atomically or not at all — a property DSH structurally cannot offer — but pins one session through every LLM call in the tree and reproduces the paper's "blocking / sequential" slowness complaint; (b) async children via `jobs`/`worker()`: concurrency and per-node crash resumability, but no tree atomicity — partial trees become normal states — and lineage must be event-tracked; (c) mixed: sync for shallow/cheap subtrees, async past a depth or cost threshold. Analysis: the paper's evidence favors async for wall-clock; PG's transactional-tree property is genuinely novel and worth keeping where subtrees are short; either way `codeact_spawn`'s `created_at DESC` child discovery must become an explicit run-id contract. *Opinion: (c), with the threshold part of the paradigm's policy bundle — and regardless of mode, emit spawn lineage as log events (restoring v1's* `'spawn'` *kind). This answers A's "does recursion bypass the event model?": today it does (`rlm_children` rows and retro-linking only); it shouldn't.*

**TC3 — Env/REPL state.** Options: (a) every env mutation is a log event, making env a fold — fully replayable, B-orthodox (no second SoT); (b) the run-scoped workspace table as-is (`rlm_vars`), the precedent B already flagged as a live second SoT; (c) a declared third tier: **workspace** — writable state that is neither history nor projection, with contract clauses (run-owned, run-lifecycle-scoped, no cross-run reads). Analysis: (a) explodes the log — every SELECT's full result lands in `last_obs` — and cannot actually replay: env values are produced by executing model-written SQL against live data, so a fold would have to re-execute non-deterministic code; (b) is honest about mechanics but silent about rules; (c) names the thing correctly — env is execution state the model addresses, closer to a TEMP table than to history, and the log already records the *code* that mutated it. *Opinion: (c). Keep the `rlm_vars` shape but contract-bound; the no-cross-run-reads boundary is exactly where Topic D's retrieval-range question bites. This answers B's `rlm_vars` question: legitimately separate — as workspace, not as history.*

**TC4 — Event vocabulary.** Options: (a) one shared log with paradigm-neutral kinds (`agent_steps` today); (b) per-paradigm logs; (c) shared envelope + paradigm-scoped kinds (B's TB1(c) shape). Analysis: (a) already overloads silently — RLM observations, spawn lineage, and paradigm-specific outcomes all squeeze into `tool`/`error`; (b) forfeits cross-paradigm folds (`run_state()`, hybrid delegation, supervision) and fragments B's projection registry; (c) keeps one SoT while letting each paradigm register its kinds, mirroring how DSH's `SessionEventMap` is interface-merged per plugin (B's evidence). *Opinion: (c); `spawn/start`, `spawn/end`, and paradigm-scoped observation kinds are the first registrations.*

**TC5 — CodeAct action surface.** Options: (a) single-tool SQL JSON action (pg-agent: one statement per turn, discrete tool calls); (b) free-form code execution in-database — true paper-CodeAct with multi-statement programs, loops, and control flow — which requires the runtime decision A deferred as T4 (`plsh`, trusted languages, C extension); (c) structured tool-call blocks (DSH): provider-native parallel calls, no code. Analysis: (a) is the proven safe subset — one statement is a natural transactional unit and the blacklist's blast radius is small; (b) maximizes paradigm power but is precisely the untrusted-code problem, and A's T4 opinion deferred it pending isolation (Topic D); (c) forfeits the database-unique composability — one `WITH` composing several workbench functions is planned as a single tree, which is parallel tool use the database gives for free. *Opinion: (a) for v0, with (b) explicitly reserved behind the T4 revisit; note the parsers already treat action-JSON and code as one field, so this is an execution-policy choice, not a protocol choice.*

**TC6 — Prompt assembly.** Options: (a) loop-internal folds (`fold_messages`/`fold_rlm_messages` as kernel functions — and note `rlm_loop` re-aggregates and re-folds **all** steps from the log on every iteration, quadratic in run length); (b) registered deterministic-fold projections (B's tier 1) with watermark checkpoints that loops consume incrementally. Analysis: (a) is simple and correct at v2 scale; (b) is the B-consistent answer — prompt assembly is the model's reading of the log, hence already a projection (DSH agrees structurally: `deriveMessages()` plus `request/header` replay) — and it fixes the quadratic refold with exactly the checkpoint machinery B imported from DSH's projection framework. *Opinion: (b); prompt assembly becomes the first consumer of the deterministic-tier projection registry, one registered fold per paradigm.*

## Open questions for D

- **Capability scoping of model-written SQL.** `exec_sql_readonly`'s keyword blacklist cannot stop side-effecting `VOLATILE` functions reachable from a plain `SELECT`. What replaces it per run/paradigm — role assumption, RLS, pinned `search_path`, or session-type separation? (Both paradigms need this; CodeAct needs it every turn.)
- **Env/workspace visibility across runs.** Spawns preset only `question` into a fresh child namespace. Should sub-agents inherit parent env or a *scoped slice* of it? This is the mechanism-level form of D's retrieval-range isolation ("project 1's code for function 1; project 2's for functions 2–3") — RLM chunk-sub-calls are its natural carrier.
- **Where async spawn children execute.** Worker sessions vs the caller's session — given that session-scoped TEMP views are today's `session_scope` workaround (A) and the `rlm.run_id` GUC is session-level, does the isolation design make run-scoped execution independent of session identity? Ties directly to A T4's dynamic-code deferral.
- **Multi-writer append ownership.** When a host-side loop (a `ReactLoopAgent` driving a pg_cordis log through a persistence seam, per B) and an in-database `rlm_loop` append to one session log: advisory locks vs serialized append transactions vs capability-gated append. Paradigm-independent, but isolation must say who may append when.
- **Budget as an isolation dimension.** The paper reports high-variance costs (outlier runs far above any base query); pg-agent's caps (`LEAST(max_steps,6)`, depth ≤ 4, ≤ 16 children, ≤ 8 map chunks) are precedent. Should a token/cost budget per subtree be enforced — and where: kernel, paradigm policy, or run row?
- **Projection visibility across paradigms/tenants.** May a projection registered by one paradigm fold runs of another (supervision folds over both `codeact` and `rlm` runs), and is that registration capability-gated? (B's tier question instantiated for paradigm logs.)

Cross-cutting: a performance budget for synchronous refolds and in-transaction LLM calls (statement-timeout interplay, A's obstacle 8); whether DSH's `ReactLoopAgent` can drive a pg_cordis log through a PG-backed persistence seam — the sharpest compatibility test of the shared substrate; migrating pg-agent's `agent_runs`/`agent_steps` vocabulary into B's richer envelope (turn/step enclosure, `surfaceOp`) without breaking `run_state()`.
