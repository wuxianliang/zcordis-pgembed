## D1 — TEMP VIEW / `session_scope` 和 yield 怎么共存

**状态：** 已拍
**决定：** **D**（新读法，不是「DA 不做」）：退役并延期 PostgreSQL `pg_temp` 数据分析路径。编码 agent v0 用 PG 做协调态（grant / selection / log / lineage）+ host worktree 做文件；分析物化留给 DuckDB 2.0 插件。禁止 **B/C**（亲和会话）。这不是暗中的 A：分析中间表不进 Postgres。
**日期：** 2026-08-23

### 为什么现在问

一步驱动已经在 scratch 上把 **claim 放掉再认领**。pg-agent v2 的 workbench（`plugin_temp_views.sql` 等）把 TEMP VIEW 当作 REPL：对象活在**当前 Postgres 后端**的 `pg_temp` 里。下一次 `worker_step()` 通常是另一条连接，`pg_temp` 是空的。不决定这一条，data_analysis 插件和「一次一步」不能同时为真。

### 背景

- v2 README：工具必须同会话，因为 TEMP VIEW 在调用者后端；所以不走 `jobs`/`worker()`。
- F §5：yield **作废** `pg_temp`。`session_scope=current_session` 跨 yield 非法，除非改成 run 级存储。
- C TC3 / D P0：env/`rlm_vars` 已经是 run 级 workspace 先例（表 `rlm_vars`，GUC `rlm.run_id`）。
- Scratch 走查用的是 `SELECT 1`，**没有**碰 TEMP VIEW，所以 9/9 PASS 证明不了 workbench。

### 选项

| 代号 | 含义 |
|------|------|
| **A** | 改成 **run 级 workspace**：视图/中间表挂在 `run_id` 上（普通表或 schema `ws_<run>`），yield 后下一任 worker 还能看见。TEMP 只作缓存。 |
| **B** | **禁止跨 yield 的 TEMP 工具**：`temp_view_mutation` 只能出现在「整段仍占着同一 claim」的路径（等于退回钉会话，或只给同步浅 spawn 用）。data_analysis 主路径不能一步一 claim。 |
| **C** | **双模式**：只读 `wb_*` 可跨 yield（不依赖 TEMP）；create/drop/curate 标成 `sticky_session`，由调度保证同一后端认领同一 run（亲和 worker）。没有亲和就拒绝这类工具。 |
| **D** | 暂缓 data_analysis workbench，一步驱动只服务纯 RLM/`SELECT`；DA 插件等 workspace 设计另开一轮。 |

### 选了会怎样

- **A**：和「一切 run 级、可换 worker」最齐，工作量大（迁移 `_wb_*`、校验器、隔离/RLS）。
- **B**：一步驱动对 DA 无意义，等于两套循环。
- **C**：实现亲和（连接池、`pg_backend_pid`、会话租约）本身像第二套 claim。
- **D**：让 yield 先在 RLM 上长，DA 明确债务。

### 依赖

挡住 D2 里「TEMP 类工具」怎么分类。不挡住纯 RLM scratch 继续做。

### Kimi_Agent / DBOS / absurd 对照

- DBOS 论文/Transact：系统状态必须是**表**，操作必须是事务；进程内存不是真相。TEMP VIEW 活在单个 backend 的 `pg_temp`，换 worker 即消失——和「双 worker 同一 claim 协议」直接冲突。
- DBOS Q12 / Apiary：长时计算、事务内等 I/O 是 non-goal；LLM 必须放在短事务之间。钉在同一会话上用 TEMP 当 REPL，等于把长循环绑回 PG worker。
- absurd：checkpoint 在 `c_` 表、worker 可互换；会话局部对象无法随 claim 交接。
- 因此 **B/C（亲和会话 / 禁止跨 yield 但仍用 TEMP 当主 REPL）** 与已锁定的 dual-worker 不一致。剩下只有 **A**（run 级表）或 **D**（DA 债务、先做纯 RLM）。

### 研究侧意见（不是决定）

建议拍 **A**。若 workbench 改造现在不做，拍 **D** 并写进债务，不要选 B/C。

愿景/oracle（2026-08-23）：改拍 **D**，读法不是「DA 不做」，而是「退役 `pg_temp` 分析路径；编码 agent 先上；DuckDB 插件后做造表」。PG 仍可有 run 级协调态（grant/selection/lineage），那不是把分析中间表做成 A。B/C 仍否决。见 `docs/analysis/2026-08-23-h-vision-d1-d9-oracle-verdicts.md`。

## D2 — Tool 在租约重叠 / 重跑时怎么办

**状态：** 已拍
**决定：** **A+C**。按能力分类：只读可重跑；能与 PG claim 同事务提交的 exactly-once；其余非事务性必须先写 `tool/call` 再副作用再写 `tool/result`。`apply_edits` / worktree / 未来 DuckDB mutation 相对 PG claim 都是非事务。崩溃看到 call 无 result：可重跑则重跑，否则标 indeterminate，禁止盲重放 mutation。
**日期：** 2026-08-23

### 为什么现在问

Oracle Q2 只保证 **LLM HTTP**。Q1 的一步却包含 tools。claim 过期或崩溃发生在 `llm` 已落、`tool` 未落时，下一任 worker 会 **再执行一遍** `rlm_eval` / `wb_*` / HTTP。不分类就会在生产里双写。

### 背景

- 今日 `emit_step` 无指纹；`sql_retry` 对 LLM 任意异常重试，工具没有对等物。
- F §5 已草拟三类：只读 SQL 可重跑；TEMP mutation 跨 yield 非法；付费/emit 要自带幂等或标不可重试。
- Absurd：step 成功则不重跑；step **外** 和进行中的副作用可能跑两次。

### 选项

| 代号 | 含义 |
|------|------|
| **A** | 按 **capability 分类**（与 workbench 的 `read_only` / `temp_view_mutation` 对齐）：只读默认可重跑；mutation / emit / 付费必须带幂等键或标 `non_retryable`（未完成则 fail 该步，不盲重放）。 |
| **B** | **整步失败即整步作废**：tools 没写完就不算 `s-N` 完成，重跑从 LLM 开始（靠 Q2 A+B 不重复计费）。工具仍可能执行两遍，只保证模型不双计费。 |
| **C** | **所有工具先写意图事件再执行**（tool/call 先于副作用），重跑看到 call 无 result 则按 A 的类处理。比 A 多一个 log 形状，接近 DSH `tool/call` + `tool/result`。 |
| **D** | 本阶段 **只允许只读工具** 进入一步驱动；其余仍走钉会话旧 `rlm_loop`。 |

### 选了会怎样

- **A**：合同清楚，要给每个工具标类；和 D1-B/D 组合时 TEMP 类直接禁跨 yield。
- **B**：实现最少，副作用双执行是已知债。
- **C**：log 更接近 DSH，迁移友好，驱动要改 emit 顺序。
- **D**：和 D1-D 一起，把范围收在 `SELECT`。

### 依赖

最好在 D1 之后。不挡住「只读 SELECT 走查」的扩大（超时抢占等）。

### Kimi_Agent / DBOS / absurd 对照

- DBOS **P0 / 洞察 I2**：必须把工具分成 **transaction（exactly-once，副作用与结果同事务）** 和 **step（at-least-once，崩溃窗口 = 副作用生效 → checkpoint 提交）**。统一假装 exactly-once 是错的。
- 写入模式：`INSERT … ON CONFLICT DO NOTHING RETURNING`，0 行则回滚再回放。错误也写 checkpoint，恢复时回放为抛错。
- absurd：公开承认 lease 窗口内 **brief overlapping execution**；外部副作用自行派生幂等键。pg_cordis 因 executor 可在库内，**事务性工具不必退到 absurd 的 lease 语义**。
- 这直接对应：只读/库内 SQL = 事务性（A 的 read_only）；LLM/HTTP/emit = 非事务（先意图后结果 = C 的 tool/call + tool/result）。选项 **B**（整步作废但工具仍可能执行两遍）等于停在 absurd 的弱保证，Kimi 明确说不要。

### 研究侧意见（不是决定）

建议拍 **A+C**：ABI 上事务性/非事务性二分；非事务工具先写 `tool/call` 再执行再写 `tool/result`；崩溃窗口写进插件合同。D 仅当 D1 也选 D 时作为范围收缩。

## D3 — sleep / await 的物理落点

**状态：** 已拍
**决定：** **B**。`jobs` 只负责任务资格（含 `available_at` / WAITING）；等待和事件用旁表 `run_waits` / `run_events`。仍是一条逻辑队列，不是第二套引擎；payload 真相在 log。
**日期：** 2026-08-23

### 为什么现在问

协议已经规定：**先把 `run/await`（或 sleep）写入 log，同一事务再放租约**。表还没选。下一步 SQL 要么往 `jobs` 加列，要么加旁表。这是 Q4「placement 开放」里最具体的一刀。

### 背景

- Absurd：每队列 `w_` 等待登记、`e_` 事件（先 emit 胜）、`schedule_run` 改 `available_at`。
- 今日 `jobs`：`PENDING/RUNNING/DONE/ERROR`，无 WAITING、无 `available_at`（scratch 驱动才加上）。
- Oracle Q3：逻辑键 `(event_scope_id, event_name)`；不需要 `LISTEN/NOTIFY` 做正确性。
- Oracle Q4：不冻 sleep/event **算不算核**，但语义不是可选的。

### 选项

| 代号 | 含义 |
|------|------|
| **A** | **全在 `jobs` 行上**：`WAITING`/`SLEEPING`、`available_at`、`wake_event_scope`、`wake_event_name`。事件唯一性用小索引表（可当折叠，payload 仍在 log）。 |
| **B** | **`jobs` 只负责任务调度**；等待/事件用旁表 `run_waits` / `run_events`（仍一张库、不是第二队列）。jobs 只被标 WAITING + 被旁表唤醒。 |
| **C** | 做成 **pg_cordis 插件 schema**（以后可拆），核只认 log 里的 `run/await` / `run/wake`，worker 轮询 log。 |
| **D** | 继续开放，scratch 只做「一步 yield」，不实现等人/sleep。 |

### 选了会怎样

- **A**：和 F 草图、scratch 已加列最贴，概念少。事件能力检查容易挤在 jobs 行上变脏。
- **B**：职责分离，更接近 Absurd，仍是一个逻辑队列。
- **C**：等于提前做 TE1「event 是插件」；轮询 log 可能慢。
- **D**：人不了、sleep 不了，异步 spawn 的「等孩子」也没有落点。

### 依赖

不依赖 D1。影响 D4（核清单里有没有 wait 表）。

### Kimi_Agent / DBOS / absurd 对照

- absurd 六表：`t_` 任务 / `r_` 运行 / `c_` checkpoint / `e_` 事件 / `w_` 等待 / `i_` 幂等键。等待和事件**从来不是**任务表上的脏列全集。
- DBOS：队列 = `workflow_status` 上的状态谓词（不是第二套队列）；`notifications` 是旁表；NOTIFY **只唤醒**。消费是 `UPDATE consumed=true … RETURNING` 且与 checkpoint 同事务。
- 已锁定「不 CREATE SCHEMA absurd 当第二队列」≠ 「不能有 e_/w_ 旁表」。旁表服务同一条 jobs/run，不是第二引擎。
- 事件锁序（absurd）：哨兵行 `FOR SHARE` → run 行 `FOR UPDATE`；first-write-wins `WHERE payload IS NULL`。应写进实现备注，不论选 A 还是 B。

### 研究侧意见（不是决定）

建议拍 **B**：`jobs` 只负责任务资格（含 `available_at` / WAITING）；`run_events` + `run_waits` 旁表抄 absurd `e_`/`w_` + DBOS 原子消费。不要选 C（把 wait 做成可选插件）或 D（继续没有等人）。

## D4 — sleep / event / retry 算不算 pg_cordis「核」

**状态：** 已拍
**决定：** **A**。五件套进核：claim、log checkpoint、sleep、scoped event、任务级 retry。D3 的旁表由核拥有。retry **状态机**在核，**曲线配置**可参数化。habitat / SDK / 分区清理仍非核。
**日期：** 2026-08-23

### 为什么现在问

Q4 窄冻只覆盖 claim + 队列 + log checkpoint。写 `CREATE EXTENSION` 或 README 时必须回答「装了 pg_cordis 自带等人吗」。这是 TE1 剩下的那一半。

### 背景

- E TE1 意见曾是：五原语（claim、checkpoint、sleep、event、retry）跟 loop kernel；habitat/SDK/分区清理当插件。Oracle 否决「现在就冻五件套」，要求先有 yield 草图——草图已有，scratch 也跑过一步驱动。
- Retry **政策**（backoff 曲线）可以是范式插件；retry **状态**（attempt、下次 `available_at`）已经像 jobs 列。

### 选项

| 代号 | 含义 |
|------|------|
| **A** | **五件套都是核**：装 pg_cordis 就有 claim、checkpoint、sleep、scoped event、任务级 retry。SDK/habitat 仍非核。 |
| **B** | **核 = 窄冻 + sleep/retry 状态机**；scoped event 当插件（人或业务事件另装）。系统级 spawn/sleep 仍在核。 |
| **C** | 维持 Q4：**核只有队列+claim+log checkpoint**；sleep/event/retry 全部插件。 |
| **D** | 与 D3 绑定：物理上在 jobs 里的就算核，旁表/插件 schema 的就不算。 |

### 选了会怎样

- **A**：产品故事清楚（「Postgres 上的 durable agent」），扩展表面积变大。
- **B**：等人可作为可选插件，但「等子 run」若也走 event，异步 spawn 会依赖插件。
- **C**：核很小，默认路径容易退回「不会等人的一步循环」。
- **D**：用存储位置当分层原则，避免空谈。

### 依赖

建议 **先 D3 后 D4**。也可一次拍「B 落点 + A 核清单」。

### Kimi_Agent / DBOS / absurd 对照

- absurd：`await_event` / `schedule_run` / `fail_run` 都在 **同一份** `absurd.sql` 引擎里，不是可选包。
- DBOS：delay、notifications、recovery_attempts 都在系统表/内核路径。
- Q4 当时「等 yield 草图再冻五件套」——F/G + scratch 三步走查已经满足该条件。
- habitat / 厚 SDK：两边都当附属（absurd 薄 SDK、DBOS 观测还外挂）。核清单不应包含 UI。
- retry **状态机**（attempt、`available_at`、死信 `MAX_RECOVERY_ATTEMPTS_EXCEEDED`）Kimi 列为 P0 移植；retry **曲线配置**可以是范式参数。

### 研究侧意见（不是决定）

建议拍 **A**：五件套进核。habitat、`absurdctl`、语言 SDK、分区清理仍非核。若只想和 D3 绑在一起：D3=B 且这些旁表由核拥有。

## D5 — Grant 的语法和谁来签发

**状态：** 已拍
**决定：** **C**（v0 枚举范围 `run` / `named_corpus:<id>` / `event:<scope>`）+ 签发政策：**模型只能申请**，写入库的是用户或受信宿主/编排器（能力持有者批准）。按 **slice** 生效，不是 run 上 grant 的并集。禁止 **B**（SQL 谓词）和 **D**（`run_id` 顶替）。升级路径仍是 A，本轮不实现。
**日期：** 2026-08-23

### 为什么现在问

D 文是隔离**提案**。Q3 已定 emit/await 是能力，但「grant 长什么样、谁写进库」会决定 RLS、事件 scope、host worker 带什么。不拍这个，隔离无法编码。

### 背景

- D P1：`(grant_id, predicate, resources, capabilities)`，按 **slice** 生效，不是 run 上所有 grant 的并集去检索。
- 工作例：项目 1 → 功能 1；项目 2 → 功能 2 和 3。Workspace 模型表达不了。
- Zleap `source` 是所有权信封（agent/user/space/thread），不是这个模型。
- 事件：一次性等人用 **不透明** `event_scope_id`，不能靠猜名字。

### 选项

| 代号 | 含义 |
|------|------|
| **A** | **结构化描述符**（resource_type + filter + capability），用户或编排器签发，模型只能**申请**、能力持有者批准。SQL 谓词不进用户输入。 |
| **B** | Grant 就是 **SQL 谓词 / RLS 表达式**。灵活，难防注入，向量检索每条路径都要带上。 |
| **C** | 第一版只做 **枚举范围**：`run` / `named_corpus:<id>` / `event:<scope>`，不做通用谓词。工作例靠两个 `named_corpus`。 |
| **D** | 隔离继续当论文；实现先只用 `run_id` 当范围（`rlm_vars`、steps）。工作例以后再做。 |

### 选了会怎样

- **A**：最像 D 提案，签发流程要产品化（谁批准）。
- **B**：和 PG 很亲，安全评审重。
- **C**：能讲清工作例，扩展性差。
- **D**：yield 可继续，隔离债务明确。

### 依赖

不挡住 D1–D4 的 RLM 一步驱动。挡住「host 带 grant 认领」和事件 scope 生命周期。

### Kimi_Agent / DBOS / absurd 对照

- **两项目都没有「检索范围 grant」。** DBOS 最多 `authenticated_user/roles`、`attributes` JSONB；absurd 有 `headers`。Kimi 原文：「两者都不覆盖的部分——agent 控制平面的插件生命周期与能力注册——仍是 pg_cordis 自己的设计空间。」
- 因此 D5 **不能**从 DBOS/absurd 推出唯一答案。工作例（项目1/项目2）仍然只有我们自己的 D 提案。

### 研究侧意见（不是决定）

第一版仍偏 **C**（枚举范围），预留升到 A。不要一上来 B（任意 SQL 谓词）。**这条必须你拍。**

愿景/oracle（2026-08-23）：已被你签名为 **C + 模型只能申请**。

附属仍开（不挡 v0 编码，实现时选偏安默认）：`named_corpus` 是整个注册项目根还是可以带版本子集；corpus 是否按 run 冻结快照；撤销怎么影响进行中的 prompt / 子 run。

## D6 — 子 run 的预算怎么传

**状态：** 已拍
**决定：** **C**。v0 只有步数/深度/扇出硬顶（沿用 v2：depth≥4、每父最多 16 子、child `max_steps = LEAST(parent, 6)`、map ≤8），在 **admission** 时检查。不做 token/费用共享池。RepoPrompt 的 selection token 预算是 context-builder 插件，不是核。
**日期：** 2026-08-23

### 为什么现在问

Q1 要「过深/过贵就异步」。pg-agent 已有硬顶：`depth≥4`、每父最多 16 子、`max_steps=LEAST(parent,6)`、`rlm_map` ≤8。没说 token/费用，也没说孩子花的步数扣不扣家长。

### 背景

- RLM 论文：BrowseComp+ 上 GPT-5 RLM 均价带很大方差。
- D P6：预算在 **run 行**，kernel 执行，范式政策参数化；如何传给孩子 **故意留空**。
- 异步 spawn 之后家长不再事务内看见孩子，预算必须是数据而不是调用栈。

### 选项

| 代号 | 含义 |
|------|------|
| **A** | **共享池**：孩子消耗扣家长剩余；耗尽则子、父都成 isolation 失败。 |
| **B** | **切块**：每个孩子得到 `LEAST(parent_remaining, cap)` 的独立预算，互不抢（接近今日 `LEAST(parent,6)`）。 |
| **C** | 本阶段 **只有步数/深度/扇出硬顶**（沿用 v2 数字），不做 token/费用。 |
| **D** | 预算完全是范式插件字段，核只提供「超预算则 fail」钩子，不定义池还是块。 |

### 选了会怎样

- **A**：控总费用，map 8 路会互相饿死。
- **B**：可预测，可能超发（8×6 步）。
- **C**：和现网一致，论文里的费用方差不管。
- **D**：核更小，各范式可能互不兼容。

### 依赖

不挡住一步驱动。挡住异步 spawn 的生产化。

### Kimi_Agent / DBOS / absurd 对照

- DBOS Q9：**不存在** token/计费预算原语，只有「checkpoint 重放不再打模型」。队列层有 concurrency / rate_limit / priority，不是 LLM 预算。
- absurd：无服务端并发上限、无优先级；只有 `cancellation.max_delay/max_duration`。
- 因此 v0.1 **发明费用共享池没有先例**；步数/深度硬顶是 pg-agent 已有的。

### 研究侧意见（不是决定）

建议拍 **C**（v0.1 只用步数/深度/扇出）。异步切块（B）等 D9 一起定。不要现在上 A 费用池。

## D7 — pg_cordis 的交付形态

**状态：** 已拍
**决定：** **D**。合同 SQL 源在 `zcordis-pgembed`；pg-agent 只当消费者测试床。现在不 `CREATE EXTENSION`。workspace / context-builder / apply_edits / 以后的 DuckDB 工作台都是 pg_cordis 插件，不是各自数据库扩展。
**日期：** 2026-08-23

### 为什么现在问

仓库 `zcordis-pgembed` 几乎还是论文 + 分析。`pgembed` 已有扩展打包套路（Makefile + `build-metadata.json` 或独立 wheel）。现在写 `CREATE EXTENSION` 可能冻太早；永远 scratch 又没有产品边界。

### 背景

- A T5 意见：先版本化 SQL（像 `v2/*.sql`），热点再 C，稳定再进 pgembed 包。
- Q4：合同应能换包装，**不能**靠包装再引进第二队列。
- Scratch 已在 pg-agent 的 pgembed 上跑，驱动 SQL 在 `zcordis-pgembed/scratch/`。

### 选项

| 代号 | 含义 |
|------|------|
| **A** | **继续 scratch SQL**：驱动留在 `zcordis-pgembed/scratch` + pg-agent 研究库，真 LLM / 超时抢占过了再谈扩展。 |
| **B** | **现在就 `CREATE EXTENSION pg_cordis`**（哪怕 0.0.1 只有 jobs 列 + claim + `rlm_step_once`），按 pgembed 独立 wheel 或 Makefile 桩。 |
| **C** | **pg-agent v2 研究分支** 合入一步驱动（新库名，不覆盖 `da_agent`），pg_cordis 扩展等合同再稳。 |
| **D** | 双轨：合同 SQL 在 zcordis-pgembed 当「扩展的 .sql 源」；pg-agent 只当消费者测试床。 |

### 选了会怎样

- **A**：迭代最快，对外仍没有「pg_cordis」物体。
- **B**：有名字有包装，API 一变就要迁移脚本。
- **C**：和现有测试（80/80 DA）抢同一套 SQL 习惯，易污染产品 v2。
- **D**：符合「插件不是数据库扩展、核才是扩展」的原话。

### 依赖

D1–D3 会改变 0.0.1 里有哪些对象。可以先选 D 的**仓库布局**，版本号以后再打。

### Kimi_Agent / DBOS / absurd 对照

- absurd：一份 `sql/absurd.sql` apply 即可，**不是**必须先 `CREATE EXTENSION`。作者目标是行为进存储过程。
- DBOS：厚 SDK + 迁移数组；库内只有 `enqueue_workflow` / `send_message`。Kimi：pg_cordis 应把「全在 PG」当对 DBOS 的推进，形态跟 absurd 而不是跟 DBOS Cloud。
- 洞察 I1：executor 即 SQL 函数。扩展包装是发行细节，不是第一周必须物。

### 研究侧意见（不是决定）

建议拍 **D**（源在本仓 `.sql`，pg-agent 当测试床）。近期不要 **B**（现在就 EXTENSION）。D1/D3 未拍前不要定 0.0.1 对象清单。

## D8 — 宿主 SDK / DSH 迁移 seam 做到哪

**状态：** 已拍
**决定：** **A** + 最小插件目录。宿主用同一套 SQL 动词（claim / checkpoint / yield / sleep / await）并查找插件元数据（identity、locus、required grants、effect/retry class）。不做 DSH 事件兼容层、不做 manifest→SQL 迁移器、不推迟宿主路径。不做动态 `node:vm` 加载。
**日期：** 2026-08-23

### 为什么现在问

「两种 worker」已锁，但宿主进程对 PG 说哪些动词、DSH 插件迁到 SQL 的工具链，都还没最小集。做大了会变成再写一个 harness。

### 背景

- DSH：一切是 Cordis 插件；动态插件走 `node:vm`；会话 log 才是模型上下文。
- A：动态 `node:vm` 建议推迟（T4）；UI 半边在库外。
- F §9：宿主用同一套 SQL 动词（claim/checkpoint/yield），自己打 HTTP 但 **同一** provider key。

### 选项

| 代号 | 含义 |
|------|------|
| **A** | **最小 seam**：libpq/SQL 调 F 的动词 + 写 `agent_steps`；不做 TS 插件加载、不做 UI。证明「host 也能一步一 claim」。 |
| **B** | 加上 **DSH session 事件形状** 的兼容层（`turn/start` 等），方便以后迁 persistence。 |
| **C** | 现在就做 **插件迁移器**（manifest → SQL 骨架）。 |
| **D** | 宿主路径整段推迟，只保证库内 `worker_step`。 |

### 选了会怎样

- **A**：兑现「双 locus」的最小证明，工作量可控。
- **B**：和 B 文 log 合同更齐，一步更大。
- **C**：在 yield/grant 未稳时易生成废 SQL。
- **D**：双 worker 锁会变成口头债。

### 依赖

A 可与 D7-D 并行。C 应在插件契约（A 文 T1/T2）更稳之后。

### Kimi_Agent / DBOS / absurd 对照

- absurd Python SDK <2000 行，全部 durable 行为在 SQL 函数里——这就是「最小 seam」的存在证明。
- DBOS Python SDK ~4 万行，「beefy SDK」被 absurd 作者点名为反面。不要抄。
- DBOS 对 agent 的态度：只做持久化原语，编排交给宿主框架。与「先 SQL 动词、不做插件迁移器」一致。

### 研究侧意见（不是决定）

建议拍 **A**。明确不做 C。D 会让已锁定的双 worker 变成口头债。

## D9 — 异步 spawn 的数字阈值

**状态：** 已拍
**决定：** **D**。每个 spawn 都是新 jobs：父请求 → 核 admission → 返回 handle → 父事务不等孩子答案。结果走 `agent_message` / 文件 / 事后 wake。CodeAct 一步内的普通 tools **不是** spawn。取消同步子树。D6 硬顶在 admission 检查。
**日期：** 2026-08-23

### 为什么现在问

Q1 D 说「过线才异步」，没给线。今日 v2：深度 4、16 子、`LEAST(parent,6)` 步、map 8 块——那是 **同步** 硬顶，不是「改异步」的线。

### 选项

| 代号 | 含义 |
|------|------|
| **A** | **沿用 v2 硬顶当同步上限**：碰到就 fail（今日行为），不自动改异步。 |
| **B** | **同一组数字改为异步阈值**：深度≥2 或 fan-out>1 就 enqueue 子 jobs，硬顶仍 fail。 |
| **C** | 阈值是范式插件配置，核只提供 sync/async 两种 spawn 动词。 |
| **D** | 第一版 **全部异步**（每个 spawn 都是新 jobs），取消同步子树（放弃事务内整树原子性）。 |

### 选了会怎样

- **A**：和现网一样，Q1 的「过线异步」不落地。
- **B**：最贴近 Q1 D，要调数字以免过早拆树。
- **C**：灵活，默认仍可能钉会话。
- **D**：实现简单，短子任务也 round-trip 队列；失去 PG 整树事务。

### 依赖

D6。不挡住只读三步走查。

### Kimi_Agent / DBOS / absurd 对照

- DBOS：同一 workflow 内并发 durable 调用会被**检测并拒绝**；fan-out 必须拆 **child workflow**（enqueue），不是嵌套在父 step 的同步 `rlm_loop(child)`。
- absurd：任务内 `spawn_task` 再 `await` 结果，孩子仍是队列上的独立 task（不是父事务里递归循环）。
- 今日 pg-agent `rlm_spawn` 同步调用 `rlm_loop(child)` 钉死父会话——正是两边都避免的形态。
- 因此 **A**（碰到硬顶只 fail、仍同步）与 Durable 先例冲突。**D**（一律 enqueue）最像 DBOS。**B** 保留「很浅仍 sync」是我们 Q1 的混合策略，DBOS 没有对等物，但是更省 round-trip。

### 研究侧意见（不是决定）

不能从 Kimi 推出唯一数字。能推出：**不要再默认同步整树**。建议你在 **D**（实现简单、放弃事务内整树）和 **B**（depth≥2 或 map 才异步）里选一个。

愿景/oracle（2026-08-23）：收窄到 **D**。prime-agent 的 `await rlm(...)` 只返回 admission handle，从不在父事务里等孩子答案。CodeAct 一步内的普通 tools 仍不是 spawn。
