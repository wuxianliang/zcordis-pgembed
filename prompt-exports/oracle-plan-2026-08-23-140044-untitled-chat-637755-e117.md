# Oracle Plan

## VERDICT

**COMBINATION A+B**

## CONFIDENCE

**High — 0.94**

## WHY

Use both mechanisms because they protect different portions of the overlap window:

1. **A — provider idempotency key is the in-flight protection.**
   - Every logical LLM step must derive one stable key from the attempt-independent identity:
     `Idempotency-Key = H(run_id, step_name)` or its canonical provider-safe encoding.
   - The key must remain unchanged across:
     - `sql_retry` retries,
     - worker retries,
     - lease expiry and takeover,
     - host-worker versus in-database execution.
   - If two workers issue the same `http_call_llm` request before either checkpoint is visible, the provider receives the same key and must return the already-created result rather than charge/execute the request twice.
   - The key must not include an attempt number, worker ID, lease ID, timestamp, or random nonce.

2. **B — log skip is the durable post-completion protection.**
   - Before making the HTTP request, the worker folds the run log and checks whether the logical step already has a completed LLM checkpoint.
   - If a matching completed checkpoint exists, the worker reuses its stored response and does not call `http_call_llm`.
   - This handles crashes or lease takeovers after the provider has completed the request and after the result has been checkpointed.
   - The checkpoint must include, or be associated with, a canonical request fingerprint. A step identity alone is insufficient: if the same `(run_id, step_name)` is presented with a different prompt, model, tool schema, or relevant LLM configuration, the worker must fail with an identity/fingerprint conflict rather than silently reuse the wrong response.

3. **The two mechanisms close complementary windows.**

   | Failure point | Required protection |
   |---|---|
   | Worker A and worker B both fold before completion is logged | Provider idempotency key, A |
   | Provider completes, worker crashes before checkpoint | Same provider key on retry, then log checkpoint, B |
   | Checkpoint is already present when a new claim starts | Log skip, B |
   | `sql_retry` retries after an ambiguous timeout | Reuse the same provider key, A |
   | Two workers race to append the same completed step | Conditional/idempotent checkpoint append keyed by `(run_id, step_name, request_fingerprint)`; conflicting payloads are errors |

The existing `http_call_llm` is `VOLATILE` and has no idempotency header, while `sql_retry` retries arbitrary exceptions. Therefore, retries currently cannot distinguish “the provider did not execute” from “the provider executed but the connection failed before the result arrived.” Reusing the same provider key is necessary to make that ambiguity safe. The log skip is still necessary because a provider key does not by itself make the worker avoid a later duplicate call once the result is durably known.

The implementation contract should therefore be:

```text
logical step identity
    → canonical request fingerprint
    → stable provider idempotency key
    → HTTP request
    → completed LLM checkpoint in the log
```

For a given logical step, the invariant is:

```text
same step identity + same request fingerprint
    ⇒ same provider key and same accepted LLM result
```

A different fingerprint for an already-completed step is a protocol violation, not a new attempt.

## REJECTED

### C — classify cheap versus side-effecting

Rejected as the primary policy.

- An LLM request is externally observable and potentially expensive even if its semantic output is “read-only.”
- The current code cannot reliably classify every request by cost, provider behavior, billing, latency, or side effects.
- A cheap-call duplicate can still produce divergent output, duplicate billing, or violate replay expectations.
- Classification is useful for optimization or telemetry, but it cannot determine whether idempotency protection is required.

### D — no claim timeout

Rejected.

- It avoids overlap only by preventing crash recovery.
- The current `worker()` behavior already leaves `RUNNING` work stuck after a worker dies, and removing lease expiry would make that failure mode contractual.
- It contradicts the locked dual-worker requirement and the purpose of durable execution.
- It also does not solve two independent `rlm_loop` executions interleaving on the same `agent_runs` row, because the current run registry has no claim ownership.

### A alone

Insufficient.

- It protects duplicate provider execution only if the provider correctly implements and honors the key.
- It does not provide the durable local fast path once the log already contains the result.
- It does not detect a request-fingerprint mismatch under the same logical step identity.
- It does not make checkpoint publication idempotent when two workers receive the same provider result.

### B alone

Insufficient.

- Two workers can both observe that the step is absent and concurrently call `http_call_llm` before either worker appends a checkpoint.
- A log fold cannot prevent duplication in that pre-checkpoint interval.
- This is particularly important for an ambiguous HTTP timeout: the provider may have completed while the worker still sees no log event.

## RESIDUAL

1. **Provider support is a hard dependency.**
   - The provider must guarantee that repeated requests with the same idempotency key return the same logical result or a defined equivalent.
   - The implementation must document behavior for timeouts, connection loss, HTTP 5xx responses, rate limits, and provider-side key expiration.
   - If a provider lacks durable idempotency-key semantics, A+B cannot guarantee exactly-once external execution; the residual fallback would require a provider-specific adapter or a database-backed request/effect ledger.

2. **The request fingerprint must cover all result-affecting inputs.**
   At minimum it should account for the canonicalized:
   - prompt/messages derived from the log,
   - model/provider,
   - generation parameters,
   - tool definitions and relevant tool version,
   - response format,
   - paradigm policy that affects the request.

   It should exclude transient attempt metadata such as worker ID and lease ID.

3. **Checkpoint publication needs a uniqueness/conflict rule.**
   The log/checkpoint fold must treat repeated completion of the same logical step as:
   - the same result: idempotent duplicate, accept;
   - a different result with the same fingerprint: consistency failure requiring investigation;
   - a different fingerprint: step identity conflict, reject and do not overwrite the first completion.

4. **`sql_retry` must preserve identity.**
   The retry wrapper around `http_call_llm` must be called with the same logical step identity and provider key on every retry. Generating the key inside a retry attempt would defeat A.

5. **This verdict covers LLM HTTP execution only.**
   It does not make model-invoked SQL/tools idempotent. Tool execution requires a separate effect/idempotency policy; the Q2 decision should not be interpreted as solving duplicate tool calls during lease overlap.

6. **The current `agent_runs` limitation remains.**
   Because `agent_runs` has no claim/ownership field, A+B protects the logical LLM step only if all workers agree on the same stable `(run_id, step_name)` identity and the log append/checkpoint path enforces the conflict rules above. It does not, by itself, prevent arbitrary interleaving of unrelated steps from two concurrent `rlm_loop` instances.
