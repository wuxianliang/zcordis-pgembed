# Oracle Plan



## VERDICT

**Choose C — emit and await are capabilities on grants**, with a constrained B-like naming refinement:

- Event names must be scoped to a **capability-bound event namespace**, not globally unique per queue.
- A tenant or grant prefix may be used internally for indexing and collision avoidance, but it is **not the authorization mechanism**.
- The event resource should be identified conceptually as:

  ```text
  (event_scope_id, event_name)
  ```

- A grant authorizes specific operations on that event resource:

  ```text
  event.emit
  event.await
  ```

- For one-shot user interactions, generate an opaque, run- or await-registration-specific `event_scope_id`; do not rely on a guessable name such as `approval` or `user_reply`.

System events such as `spawn`, `sleep`, and `wake` remain reserved kernel events. They use the same durable log and authorization machinery, but user/business events are also required.

## CONFIDENCE

**High — 0.94.**

The conclusion follows directly from the locked retrieval-range isolation model and does not depend on yield-boundary or LLM-idempotency decisions.

## WHY

1. **Names do not provide isolation.**  
   A queue-global name creates a single collision and visibility domain, while D's model permits one run to hold multiple grants bound to different slices. A run with project-1 and project-2 grants must not automatically be able to observe or emit every event associated with both grants.

2. **Option A creates both a confidentiality and availability problem.**  
   With globally unique, guessable names, a caller can:

   - probe whether an event exists;
   - await another tenant's event;
   - emit an event first and win the immutable first-emit-wins race;
   - prevent the legitimate emitter from publishing the intended payload.

   Absurd's queue-level uniqueness is therefore a useful execution semantic, but not an adequate pg_cordis isolation boundary.

3. **Option B addresses naming collisions but not authorization.**  
   Automatically adding a tenant or grant prefix distinguishes names, but it does not answer:

   - who may await the event;
   - who may emit it;
   - whether the caller may see the payload;
   - whether a slice may use the event when the same run holds other grants.

   Prefixing should be treated as a storage or routing detail derived from the authorized event scope, never as proof of access.

4. **Option C matches D's grant model.**  
   Retrieval, fold access, tool execution, environment access, event emission, and event awaiting all become operations authorized against the active slice's grants. The run's union of grants must not be used for event lookup; only the current slice's live grants may authorize the operation.

5. **Option D is insufficient for the required execution model.**  
   System-only events support kernel mechanics but leave no durable mechanism for:

   - waiting for a user approval;
   - waiting for an uploaded file or external callback;
   - waiting for a business-domain event such as `shipment.packed`;
   - resuming a run after a user interaction without pinning a PostgreSQL session.

   DSH's capability-scoped questions and approvals are direct evidence that user-facing waits are part of the required control surface, not an optional product feature.

6. **The session log remains the source of truth.**  
   An event index or uniqueness structure may enforce first-emit-wins efficiently, but the event payload and resolution facts must be appended to the existing log. Event tables or indexes may be projections/constraints; they must not become an independent authoritative history.

## REJECTED

### A — Global unique names

Rejected as the event authorization model.

Queue-global uniqueness may remain an implementation property for a deliberately shared system channel, but it must not be the default namespace or visibility rule. A name must not be discoverable or usable merely because it is syntactically valid.

### B — Automatic grant/tenant prefixes

Rejected as the sole design.

A derived prefix can be retained as an internal optimization:

```text
storage_key = (derived_event_scope_id, event_name)
```

However, authorization must still validate the caller's `event.emit` or `event.await` capability against that scope. A tenant prefix is too coarse for project-level, run-level, slice-level, and one-shot user-interaction channels.

### D — System events only

Rejected.

Keep `spawn`, `sleep`, `wake`, and similar events in a reserved system namespace, but support user/business events through the same capability-controlled mechanism. In particular, `await-user` must be a normal durable wait operation resolved by an authorized user-side emitter.

### Raw, unrestricted C

Also reject an overly broad interpretation of C in which possession of any grant permits awaiting or emitting arbitrary event names within that grant's data range. Event permissions must bind to an event resource or selector, not merely to an unrelated retrieval grant.

## How `await-user` should work

### 1. Create an authorized one-shot event channel

The orchestrator or user-facing control plane creates an opaque event scope for the interaction, for example conceptually:

```text
event_scope_id = random, non-guessable channel identifier
event_name     = "user_reply"
```

The grants are split by operation:

- the running slice receives `event.await` for this exact event resource;
- the UI, authenticated user actor, or callback service receives `event.emit` for the same resource;
- neither side receives broader event access unless explicitly required.

The event scope should normally be tied to the run or await registration and have an expiry. Reusable business events can use a deliberately shared scope, but that must be an explicit grant decision.

### 2. Persist the wait before releasing execution

When the active loop invokes `await-user`:

1. Validate that the active slice has `event.await` for the target event resource.
2. Append a `run/await` event to the session log containing:
   - await-registration identifier;
   - event scope and logical name;
   - deadline or timeout policy;
   - user-facing request metadata needed by the authorized UI;
   - the continuation/resume boundary.
3. Transition the durable run/job state to `WAITING`.
4. Commit the transaction and release the worker claim/session.

The operation must not hold a PostgreSQL session, transaction, or lease while waiting.

### 3. Resolve the event through the authorized emitter

The UI or callback service submits the user's response through an authenticated emit operation:

1. Validate the `event.emit` capability for the exact event resource.
2. Atomically apply first-emit-wins for that scoped resource.
3. Append an `event/emit` log event containing the immutable payload.
4. Append a `run/wake` log event referencing the emitted event's sequence number rather than duplicating its payload.
5. Mark the matching await registration resolved and make the run available to the shared worker protocol.

The user-facing emitter must not be allowed to write `run/wake` directly. It emits the business event; the kernel derives the wake transition.

No `LISTEN/NOTIFY` path is required for correctness. Polling or normal worker claim logic can observe the durable availability transition; notifications may be added later only as a latency optimization.

### 4. Resume using the log fold

When a worker claims the run:

1. The run's authorized slice fold reads the `run/await`, `event/emit`, and `run/wake` facts.
2. The continuation receives either:
   - the authorized user payload; or
   - a typed timeout/cancellation result.
3. The loop resumes after the await boundary, rather than re-running the preceding work.

The event payload must only be exposed through a fold or retrieval path authorized by the await capability. Merely knowing the event name must not reveal whether the event exists or what it contains.

### 5. Define races and duplicates explicitly

- **Emit before await:**  
  If the caller has the required capabilities, the later await resolves immediately from the already committed immutable event.

- **Await before emit:**  
  The run remains `WAITING` until the authorized emitter publishes or the deadline resolves.

- **Concurrent emitters:**  
  A transactionally enforced uniqueness rule on `(event_scope_id, event_name)` selects one winner. The losing emitter cannot replace the payload.

- **Duplicate emit retry:**  
  A retry with the same idempotency key returns the original resolution. A different payload after resolution is rejected or reported as already resolved; it must not append a second authoritative event.

- **Duplicate wake processing:**  
  The await-registration state transition is compare-and-set/idempotent. A worker retry may observe the same log facts, but it must not create a second logical continuation.

- **Timeout versus user response:**  
  Timeout and emit compete in one atomic resolution transition. Whichever commits first wins. For the default one-shot user channel, a late response after timeout is rejected or ignored and cannot wake the run.

- **Dropped callback:**  
  The run stays durably `WAITING` until the event or timeout arrives. The callback can be retried without losing the request.

- **Unauthorized lookup or emission:**  
  The operation fails before event existence or payload is disclosed. External APIs should use an authorization failure shape that does not provide an event-existence oracle to callers lacking the relevant grant.

This gives pg_cordis durable user interaction without introducing a second event source of truth, while preserving grant-scoped isolation for both system and business events.
